  <how-to-verify>
    Ensure you are on a live Qt 6 xcb display (D-28). Then run:

    ```bash
    cd $MEFISTO
    QT_QPA_PLATFORM=xcb pp/ppxvtest0_qt
    ```

    During the FIRST SLEEP(10) hold, visually verify the following checks.
    All checks must pass for approval.

    1. **DejaVu Sans Mono font loaded (TEXT-01):** Every text label on the
       canvas is rendered in a crisp monospace font with smooth (not
       pixelated) glyph edges. If labels look like a sans/serif proportional
       font, addApplicationFont failed silently — Pitfall 1 not handled.
       If glyph edges are jaggy, QPainter::TextAntialiasing was not asserted
       (plan 03-01 Task 1 Step 7 regression).

    2. **8 distinct colored lines and labels (TEXT-03 + TEXT-04 + palette
       defaults):** Eight short horizontal lines stacked vertically (y
       ≈ 100..275), each followed by a "COLOR-0" through "COLOR-7" label.
       Each line must be a DIFFERENT color matching the imposed-default
       palette: index 0 = black (may be invisible on black background — if
       you cannot see line 0, that's expected), index 1 = red, index 2 =
       green-ish, index 3 = blue-ish, and so on per the xvuelc.c:378-461
       table. If all 8 lines are the same color, palette_cache_ or
       xvcouleur_ is broken. If indices match the Qt::Global enum values
       (e.g. Qt::red = pure 255,0,0) instead of the legacy values, the
       imposed_defaults_fill lift was paraphrased — regression.

    3. **xvactivervb_ bulk-load line (TEXT-05):** One additional horizontal
       line at y ≈ 320 in a COLOR OTHER THAN the imposed defaults — the
       RVB-CUSTOM color the driver loaded via xvactivervb_ into index 8
       (something like `(0.8, 0.2, 0.5)` — value driver-dependent, see
       prpr/xvtest0.f Phase 3 section). Followed by an "RVB-CUSTOM" text
       label. If the line is the same color as any of the 8 imposed
       defaults, xvactivervb_ is silently no-op'ing and A3 was not honored.

    4. **xvnbpixeltexte_ measured label + bounding box (TEXT-02):** A text
       label reading "MESURE-XVNBPIXELTEXTE" at y ≈ 360 with an OUTLINED
       rectangle drawn around it whose width matches the glyph run within
       a few pixels. The box must NOT clip any glyph and must NOT be more
       than ~10 pixels wider than the text. If the box is dramatically
       larger or smaller than the glyph run, horizontalAdvance is returning
       wrong values or the Fortran caller is using a stale metric.

    5. **Resize preserve + no color drift (DRAW-09 regression + TEXT-06):**
       While the window is held by SLEEP, grab an edge and drag to RESIZE
       the window LARGER. The previously drawn content must remain anchored
       at the top-left, with new area filled in the current background
       color. ALL colors of the pre-resize lines and labels must be
       UNCHANGED after the resize (no dark-mode style leaking into the
       backing pixmap, no palette_cache_ being rebuilt with different
       values).

    6. **Reopen cycle (SHELL-02 regression):** After the first XVFERMER,
       the second XVINITGRAPHIQUE opens cleanly with no "QApplication:
       there can only be one" assertion. The second SLEEP hold shows a
       blank canvas (by design — the driver does not redraw the Phase 3
       section in the second cycle).

    7. **Process exit clean:** After both cycles, `echo $?` prints 0. No
       SIGSEGV, no Qt warnings about "Painter not active", no "QPixmap:
       Must construct a QGuiApplication first", no "QFont: could not find
       font family DejaVu Sans Mono".

    Optional HiDPI sanity check: `QT_SCALE_FACTOR=2 QT_QPA_PLATFORM=xcb pp/ppxvtest0_qt`
    should produce the same visual layout at 2x scale (Phase 1 SHELL-06
    regression guard).
