# Phase 02.1: Code Review Report

**Reviewed:** 2026-04-13
**Depth:** standard
**Files Reviewed:** 1
**Status:** issues_found (info-level only)

## Summary

The phase-02.1 change to `xvfacetraits_` correctly mirrors the legacy
contract from `xvue/xvuelc.c:2055,2064`:

1. install `*ncf` as foreground, fill the polygon (pen suppressed so the
   fill step cannot stroke an edge — WR-01);
2. install `*nca` as foreground, outline the polygon (brush suppressed so
   the outline step cannot re-fill — WR-01);
3. leave `foreground_` at `nca` on exit, matching the legacy final-state
   invariant.

The new file-local helper `apply_palette_foreground` faithfully reproduces
the body of `proc(xvcouleur)` (lines 354–371) minus the
`XvueApp::ensure()` / thread-assert / window-slot re-lookup, which is
correct because callers that already hold a resolved `XvueState*` have
completed those checks.

Correctness of the Fortran/C ABI contract is preserved (signature
unchanged, pointer null-checks on every `in` argument, `*n < 3` guard).
Polygon closure is correctly handled: the legacy contract passes
`pts[0] == pts[n-1]`, so Qt's auto-closing `drawPolygon` outline draws a
zero-length closing segment that is visually indistinguishable from
`XDrawLines(..., n, ...)`'s explicit closing segment.

No critical or warning issues. Three info-level observations below.

## Info

### IN-01: Dead pen restore between fill and outline steps

**File:** `xvue/qt/src/xvue_qt_api.cpp:725-728`
**Issue:**
```cpp
apply_palette_foreground(st, *ncf);
QPen   saved_pen_after_ncf = st->painter_->pen();
st->painter_->setPen(Qt::NoPen);
st->painter_->drawPolygon(poly, Qt::OddEvenFill);
st->painter_->setPen(saved_pen_after_ncf);          // <-- no observable effect
```
The restored pen is immediately discarded by the subsequent
`apply_palette_foreground(st, *nca)` call on line 730, which invokes
`XvueState::applyPen()` and unconditionally rebuilds `pen_` from
`pen_style_` + `foreground_` (see `xvue_qt_state.cpp:136-142`). The
restore is dead work.

Keeping the restore is defensible as belt-and-braces (it makes the
fill-only transient state local to the block), but the code comment on
lines 720-723 implies the restore is needed so "the dashed style set by
`xvtypetrait_` survives the outline step," which is misleading — the dash
survival is actually carried by `pen_style_` through the second
`applyPen()` call, not by the saved pen.
**Fix:** Either (a) drop the save/restore pair and let `applyPen()` do the
rebuild explicitly, or (b) update the comment to state that the restore
is defensive and that dash-style survival is mediated by `pen_style_`
through `applyPen()`. Recommend (b) for minimal churn:
```cpp
// Defensive pen restore: subsequent apply_palette_foreground() will
// rebuild the pen from pen_style_+foreground_ via applyPen(), so dash
// survival does NOT depend on this restore. Kept to make the fill-only
// state (Qt::NoPen) strictly local to the fill step.
st->painter_->setPen(saved_pen_after_ncf);
```

### IN-02: Palette clamp/rebuild logic triplicated

**File:** `xvue/qt/src/xvue_qt_api.cpp:354-368`, `465-477`, `689-701`
**Issue:** The palette-index clamp + dirty-cache rebuild block is now
duplicated in three places: `proc(xvcouleur)`, `proc(xvfond)`, and the
new `apply_palette_foreground` helper. `proc(xvfond)` differs only in the
fallback index (0 instead of 1) and does not call `applyPen()`. The three
copies are prone to drift if the palette-cache policy changes (e.g. alpha
channel, gamma).
**Fix:** Follow-up cleanup (not blocking for 02.1): extract a shared
`palette_resolve(int icolor, int fallback) -> const QColor&` that
encapsulates the clamp + dirty-cache rebuild, and let the three callers
decide whether to write `foreground_` / call `applyPen()` / set
`background_`.

### IN-03: Brush-restore comment partially stale

**File:** `xvue/qt/src/xvue_qt_api.cpp:733-737`
**Issue:** Comment says "Legacy leaves foreground at nca; do not restore.
Brush is left at Qt::NoBrush but the next applyPen()/xvcouleur_ call
will refresh it." The very next statement (line 737) then DOES restore
the brush defensively to `QBrush(st->foreground_, Qt::SolidPattern)`,
which contradicts the preceding sentence. The reader has to infer that
the first two sentences describe the contract and the third (WR-04)
tightens it.
**Fix:** Rewrite the comment block so the contract statement and the
WR-04 tightening are not adjacent contradictions:
```cpp
// Legacy leaves foreground at nca; we match that by not touching
// foreground_. The fill/outline swaps above left the painter brush at
// Qt::NoBrush, which is valid because any subsequent xvcouleur_/
// applyPen_ call would refresh it. WR-04 tightens this: we restore the
// brush to match st->foreground_ so primitives that read the live
// painter brush (e.g. xvface_) see the canonical post-ncf->nca state
// without needing an intervening xvcouleur_ call.
st->painter_->setBrush(QBrush(st->foreground_, Qt::SolidPattern));
```

## Adjacent pre-existing code (spot-checked, no issues to flag)

- `proc(xvface)` (lines 585-608): correct WR-01 pen-suppress pattern,
  `*n < 3` guard, null checks — consistent with the new `xvfacetraits_`.
- `proc(xvtraits)` (lines 657-684): stack-vs-heap split at
  `STACK_LIMIT = 128` is sound; `*nbpoints < 2` guard is correct for a
  polyline (minimum two points).
- `apply_palette_foreground` (lines 689-701): does not null-check `st`,
  but this is acceptable because it is `static` (file-local) and both
  call sites in `xvfacetraits_` have already validated `st` and
  `st->painter_->isActive()`. A defensive assert could be added but is
  not required.
- Legacy contract cross-check against `xvue/xvuelc.c:2055,2064`: the two
  `proc(xvcouleur)` calls bracket the fill and the outline in the exact
  order the Qt port now mirrors. The Qt port additionally suppresses
  pen/brush at each step — necessary because Qt's `drawPolygon`
  strokes-and-fills by default whereas Xlib's `XFillPolygon` /
  `XDrawLines` are strictly separate primitives.
