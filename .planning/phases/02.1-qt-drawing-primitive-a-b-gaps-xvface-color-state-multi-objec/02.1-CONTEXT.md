<decisions>
## Implementation Decisions

### D-1: Fix xvface_ per-face color state (xvtest2 triangles + xvtest4 inscribed tetrahedron)
- The Qt `xvface_` implementation does not preserve the foreground color set by the preceding `xvcouleur_` call across successive face draws, OR it overwrites the brush before the fill happens.
- **Evidence:** xvtest2.f draws a magenta hex outline, then a red triangle (xvcouleur→red, xvface), then a blue triangle (xvcouleur→blue, xvface). Qt shows only the inner white fill of the last face call. X11 shows all three fills plus the outline.
- **Suspected files:**
  - `xvue/qt/src/xvue_qt_api.cpp` — `xvface_`, `xvcouleur_`, `xvtrait_`, `xvtraits_`
  - `xvue/qt/src/xvue_qt_canvas.cpp` — `applyPen`, brush state flush
  - Any state struct holding the current `QBrush` / `QPen`
- **Target fix:** ensure that each `xvface_` entry reads the *current* foreground color from the state (the value set by the most recent `xvcouleur_`) and creates the `QBrush` at fill time, not at init or at polygon-start time.
- **Reference contract:** `xvue/xvuelc.c::xvface_` and its surrounding helpers are the authoritative semantics. Do not copy C code — re-implement the same contract in C++/Qt.

### D-2: Fix multi-object 3D composition (xvtest4 inscribed tetrahedron dropped)
- xvtest4.f draws a cube, then an inscribed tetrahedron with a red face. Qt only shows the cube.
- **Suspected cause:** either the polygon stack / z-buffer is cleared between objects, or a second call chain (`xvface_` for the tetrahedron) hits a state where the painter is no longer active or the vertex list was reset.
- **Target fix:** verify that consecutive draw-object sequences accumulate on the backing pixmap without clearing between them, matching the legacy semantics.
- **Reference contract:** legacy `xvuelc.c` keeps the X11 drawable as a persistent target until `XVINIT`/`XVINITGRAPHIQUE` is called again.

### D-3: Implement dashed pen style (xvtest4 cube edges shown solid in Qt)
- legacy X11 renders xvtest4 cube edges with a dashed stroke; Qt renders them solid. Either the `xvtraits_` pen-style parameter is being ignored, or the mapping to `Qt::DashLine` / `QPen::setDashPattern` is missing.
- **Suspected files:** `xvue/qt/src/xvue_qt_api.cpp::xvtraits_`, `xvue/qt/src/xvue_qt_canvas.cpp::applyPen`
- **Target fix:** map the legacy line-style integer (check `xvtypetrait` / `xvtraits` in `xvuelc.c` for the enum values) to `Qt::PenStyle` values. At minimum support: solid, dashed. Dotted/dashdot are nice-to-haves if the same switch statement is cheap to fill out.

### D-4: Do NOT touch xvuelc.c, xvouvrir.f, or xvue_qt_api.h
- Preserve X11 bit-identity (BUILD-07).
- Preserve cross-backend symmetry.
- Keep the ABI at its current count (57 exports). No new `extern "C"` symbols introduced.

### D-5: Validation is observable, not mock-based
- Every fix must be verified by re-running `ppxvtest2_qt` / `ppxvtest4_qt` under `QT_QPA_PLATFORM=xcb` on Xvfb :99 and comparing against the legacy `ppxvtest2` / `ppxvtest4` captures already committed at `.planning/phases/03-text-fonts-colormap/03-04-ab/xvtest{2,4}_x11.png`.
- Pixel-level image diff is optional; the D-27 rubric (geometry present, colors match, no miscolored regions) is the primary acceptance criterion.
- Automated verify: grep the Qt capture for the dominant color pixels (red, blue, magenta) that are currently missing. Simple `convert capture.png -unique-colors txt:` counts the palette; compare to a minimum-unique-colors threshold.

### D-6: Work on the Qt build only — the legacy X11 build does not need to re-green
- `bin/cbl_tout_qt` must stay green.
- `bin/cbl_tout` (legacy) is not expected to re-run in this phase — the legacy X11 crashes in `xvuelc.c` are pre-existing and out of scope.
- `verify_abi` target must still pass (nm count = header count).
- `verify_no_exec` must still pass (no `QApplication::exec`, no palette leak).

## Specific Ideas

- The verify loop for each plan should include a "convert capture.png -unique-colors txt: | wc -l" check: xvtest2 broken Qt capture has ~3 unique colors (black, white, yellow, red-text, green-text, cyan-text, red-text); the fix should bring unique colors above 6 (adds red and blue fills). xvtest4 broken Qt capture has ~2 unique colors (black, white); fix should bring it above 4 (adds red, blue, dashed-edge rendering).
- The xvtest0_qt driver (already passing) is a known-good reference — whatever state-management pattern it uses for polygon drawing should be the baseline for fixing xvface_.
- The fix may be as small as "flush the brush before QPainter::drawPolygon" if the current code sets the brush at face-start time but doesn't apply it again after intervening xvcouleur_ state changes.

</specifics>
