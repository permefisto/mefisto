# Phase 02.1: Qt drawing-primitive A/B gaps - Research

**Researched:** 2026-04-12
**Domain:** Qt 6 (QPainter / QPen / QBrush) backend for legacy X11 GC drawing primitives
**Confidence:** HIGH
**Phase scope:** narrow bug fix - close three identified gaps in `xvue/qt/src/`. No refactor.

## Summary

The Phase 03-04 A/B gate (xvtest2 + xvtest4 under `QT_QPA_PLATFORM=xcb` on Xvfb :99) failed because the Qt backend `xvfacetraits_` body deliberately ignores its color arguments. After reading both backends side by side, the entire failure surface collapses to **one root cause** plus **two false leads** that the escalation report listed as separate suspects:

1. **Real bug (single root cause for both xvtest2 and xvtest4 visual failures):** `xvue/qt/src/xvue_qt_api.cpp::xvfacetraits_` (lines 687-718) explicitly drops the `ncf` and `nca` color arguments via `(void)ncf; (void)nca;` and a `TODO(phase 3)` comment. The fill therefore renders with whatever foreground color happens to be active from the previous `xvcouleur_` call, instead of switching to `ncf` for the fill and `nca` for the outline. The legacy `xvue/xvuelc.c:2035-2110::xvfacetraits_` does this color switch via two internal `xvcouleur_(ncf)` then `xvcouleur_(nca)` calls before `XFillPolygon` and `XDrawLines` respectively.

2. **NOT a bug — `xvface_` per-face color state:** the Qt `xvface_` body (lines 585-608) is correct. It reads brush from `state_->painter_->brush()`, which is the brush installed by `applyPen()` from the most recent `xvcouleur_`. Both `xvtest2.f` and `xvtest4.f` reach `xvface_` via the Fortran wrappers `face2d.f` / `face3d.f`, which always go through `XVFACETRAITS` for the `(NCF≥0, NCA≥0)` triangle case (xvtest2 line 46-49, xvtest4 OBJET3D lines 120-129). The `XVFACE` path is only taken when `NCA<0` (xvtest4 line 124-125). So the visible "missing red and blue triangles" all come from `xvfacetraits_`, not `xvface_`.

3. **NOT a bug — multi-object 3D composition / "inscribed tetrahedron dropped":** the escalation report's hypothesis is wrong. There IS no inscribed tetrahedron in `xvtest4.f`. The driver only draws `XYZ` (a unit cube as 10 triangle faces in `OBJET3D`); `XYZR` is declared but never passed to `OBJET3D`. The "missing tetrahedron" the operator saw in the X11 capture is actually the same 10-triangle cube but with the **red face (4,8,5) and blue triangles (3,7,6)/(3,8,7)/(6,7,8)** correctly colored — the Qt capture is missing exactly those colored triangles. Same root cause as xvtest2: `xvfacetraits_` is not honoring `ncf`. There is no separate composition / state-clearing bug.

4. **NOT a bug — dashed pen style (`xvtypetrait_`):** the Qt `xvtypetrait_` body (lines 611-621) correctly stores `*ptype` into `state_->pen_style_` and calls `applyPen()`, which maps 0→`SolidLine`, 1→`DashLine`, default→`DashLine`+double width. xvtest4 line 53 calls `XVTYPETRAIT(1)` and the cube edges are drawn through `xvfacetraits_`'s `drawPolygon` outline step using the current pen. **The reason the Qt capture shows solid edges is not the pen style — it is that the edge color (magenta from `nca=NCMAGE`) is also being dropped**, and the edge ends up rendered in the same wrong color as the fill (white), making it visually invisible against the white fill and giving the false impression that the edge is missing or that the dash is gone. Once the `nca` color is honored, the magenta dashed outline will become visible because the dashed style is already correctly active. This needs an A/B re-capture to confirm — but the code path is already wired.

**Primary recommendation:** Fix `xvfacetraits_` to call (or inline) `xvcouleur_(ncf)` → fill → `xvcouleur_(nca)` → outline, exactly mirroring `xvue/xvuelc.c:2055,2064`. Restore the prior foreground at the end so the caller sees no state drift — the legacy backend leaves it at `nca` and Fortran wrappers tolerate that. ABI count stays at 57. Total expected change: ~15 lines in one function, in one file. Validation is a re-run of the existing A/B captures.

### False leads from the escalation report

- **"`xvface_` is dropping per-face brush color across successive draws"** — wrong. `xvface_` is correct. The relevant call site for the missing triangles is `xvfacetraits_` because `face2d.f:78`/`face3d.f:91` go through `XVFACETRAITS` whenever both `NCF≥0` and `NCA≥0`.
- **"Polygon stack / z-buffer cleared between objects in xvtest4"** — wrong. There is no second object. xvtest4.f only draws the cube via `OBJET3D(XYZR, XYZ)` 320 times (an animation loop). `XYZR` (the supposed tetrahedron coordinates) is passed as the first argument but **`OBJET3D` ignores it** — see the body at xvtest4.f:106-130 which only references `XYZ`. The "missing inscribed tetrahedron" in the operator's mental model is actually the missing colored triangles of the cube itself.
- **"Dashed pen style is a no-op on Qt side"** — wrong. The pen-style switch in `applyPen()` is implemented and correct. The visible symptom is downstream of the color-switch bug.

## Architecture Patterns

### Recommended fix structure

The phase has exactly one code change point. The pattern is "patch the function body, preserve the existing scaffolding."

```
xvue/qt/src/xvue_qt_api.cpp::xvfacetraits_  (edit ~15 lines, ~line 687-718)
   |
   +-- Step 1: read Phase 02 D-12 split (fill then outline) — preserve
   +-- Step 2: BEFORE the fill, switch foreground to *ncf and applyPen()
   +-- Step 3: BEFORE the outline, switch foreground to *nca and applyPen()
   +-- Step 4: (optional) save original foreground at top, restore at end
```

### Pattern: in-function color switch (mirror legacy)

**What:** Inline the two `xvcouleur_`-equivalent operations inside `xvfacetraits_` rather than calling `proc(xvcouleur)` itself (avoids re-doing the `XvueApp::ensure()` + thread assert + window lookup three times in one entry point).

**Reference (legacy):**
```c
// xvue/xvuelc.c:2055-2065
proc(xvcouleur)( ncf );
XFillPolygon(display_mef, mempx, gc_mef, pts, *n, Complex, CoordModeOrigin);
/* ... save courgb for postscript ... */
proc(xvcouleur)( nca );
XDrawLines( display_mef, mempx, gc_mef, pts, *n, CoordModeOrigin );
```

**Target Qt skeleton (for the planner — not final code):**
```cpp
// xvue/qt/src/xvue_qt_api.cpp::xvfacetraits_
void proc(xvfacetraits)(int *ncf, int *nca, int *n, MefistoPoint *pts) {
    XvueApp::ensure();
    XVUE_QT_ASSERT_MAIN_THREAD();
    if (!ncf || !nca || !n || *n < 3 || !pts) return;     // WR-03
    auto& win = XvueApp::window_slot();
    if (!win) return;
    auto* st = win->state();
    if (!st || !st->painter_ || !st->painter_->isActive()) return;

    // Build polygon once
    QPolygon poly;
    poly.reserve(*n);
    for (int i = 0; i < *n; ++i) poly << QPoint(pts[i].x, pts[i].y);

    // --- D-12 split: fill (ncf) ---
    set_palette_foreground(st, *ncf);   // inline xvcouleur_ body OR helper
    QPen   saved_pen = st->painter_->pen();
    st->painter_->setPen(Qt::NoPen);
    st->painter_->drawPolygon(poly, Qt::OddEvenFill);

    // --- D-12 split: outline (nca) ---
    set_palette_foreground(st, *nca);
    st->painter_->setBrush(Qt::NoBrush);
    st->painter_->drawPolygon(poly);    // uses current pen (incl dash style)
    // Restore Qt-side painter scaffolding
    st->painter_->setPen(saved_pen);
    st->painter_->setBrush(QBrush(st->foreground_, Qt::SolidPattern));

    if (win->canvas()) win->canvas()->update();
}
```

The legacy backend leaves foreground at `nca` after the call; planner can choose either "leave at nca" (matches legacy) or "save+restore original" (defensive). Recommend matching legacy.

### Anti-patterns to avoid

- **Adding a new ABI symbol.** `verify_abi` will fail the build. Count stays 57.
- **Touching `xvouvrir.f` or any `xvue/*.f` Fortran wrapper.** Cross-backend symmetry breaks, `cbl_tout` would diverge from `cbl_tout_qt`.
- **Touching `xvue_qt_api.h`.** ABI freeze.
- **Calling `proc(xvcouleur)` from inside `xvfacetraits_`.** Works but duplicates the `XvueApp::ensure()` / thread-assert / window-slot lookup three times per call. Inline or factor a tiny private helper.
- **Refactoring `applyPen` / state struct.** Out of scope.

## Common Pitfalls

### Pitfall 1: Calling `proc(xvcouleur)` inside `xvfacetraits_` and assuming it's free

**What goes wrong:** triple `XvueApp::ensure()` + triple thread assertion + triple window-slot lookup per face. xvtest4 calls `OBJET3D` 320 times which triggers `xvfacetraits_` 7-10 times per iteration → 2240-3200 calls per frame. The window-slot and thread-assert overhead is small but the duplicated work is gratuitous.
**Why it happens:** copy-paste fix from the legacy reference, where these helpers don't exist.
**How to avoid:** inline the palette-cache lookup, or factor a tiny `static` helper that takes the already-resolved `XvueState*`.
**Warning signs:** xvtest4 frame rate visibly slower after fix.

### Pitfall 2: Forgetting `setBrush(Qt::NoBrush)` for the outline step

**What goes wrong:** the outline pass also re-fills with the edge color, double-painting the polygon. Wastes work and potentially produces a thicker visible edge if the brush is dense.
**Why it happens:** `applyPen()` always sets brush from foreground. After switching foreground to `nca`, brush is also `nca`. Calling `drawPolygon` will fill AND stroke unless brush is killed.
**How to avoid:** match the existing pattern at lines 710-715 — `setPen(Qt::NoPen)` for fill step, `setBrush(Qt::NoBrush)` for outline step.
**Warning signs:** the outline step paints over the fill in the edge color.

### Pitfall 3: Leaving `Qt::NoBrush` installed at function exit

**What goes wrong:** subsequent `xvface_` calls render with no fill (because brush is `NoBrush` until next `xvcouleur_`).
**Why it happens:** forgetting to restore brush at function exit.
**How to avoid:** at exit, re-`applyPen()` (cheap) OR explicitly `setBrush(QBrush(st->foreground_, Qt::SolidPattern))`. The skeleton above does the latter.
**Warning signs:** the *next* face after `xvfacetraits_` renders as unfilled outline only.

### Pitfall 4: Restoring foreground to "original" instead of leaving it at `nca`

**What goes wrong:** subtle drift from legacy semantics. Legacy leaves foreground at `nca` after `xvfacetraits_` returns; Fortran wrappers (e.g., `face2d.f`, `face3d.f`) re-set color via the next `xvcouleur_` before drawing anything else, so they never observe the leftover. But if some caller in the wider codebase does NOT re-set color, it would see the legacy backend's `nca` and the Qt backend's "original" — that's a divergence.
**Why it happens:** "defensive" save+restore feels safer.
**How to avoid:** match legacy. Leave foreground at `nca`.
**Warning signs:** A/B capture diff on a non-xvtest driver after the fix.

### Pitfall 5: Re-introducing dashed-style symptoms by accident

**What goes wrong:** the "dashed edges missing" symptom in xvtest4 is currently a downstream effect of the color bug. Once the fix lands, the magenta edges should appear AND already be dashed (because `xvtest4.f:53` set `XVTYPETRAIT(1)` and the Qt pen style is wired). If after fix the edges appear solid, that means `applyPen()` is being called with a stale `pen_style_` somewhere.
**Why it happens:** unlikely, but if the planner adds a `setPen()` call that constructs a fresh pen instead of reusing `state_->pen_`, the dash style would not propagate.
**How to avoid:** always reuse `state_->pen_` (which was built by `applyPen()`), never construct a fresh `QPen`. The skeleton above does this implicitly via `saved_pen = st->painter_->pen()` (which is the painter's current pen that `applyPen` last set).
**Warning signs:** A/B re-capture shows colored magenta cube edges but they are solid instead of dashed.

```cpp
// Source: xvue/qt/src/xvue_qt_api.cpp:362-371 (xvcouleur_ palette-cache pattern)
static inline void set_palette_foreground(XvueState* st, int icolor) {
    int i = icolor;
    if (i < 0 || i >= XvueState::kMaxPalette) i = 1;     // legacy "fallback to red"
    if (XvueState::palette_cache_dirty_[i]) {
        XvueState::palette_cache_[i] = QColor::fromRgbF(
            XvueState::red[i],
            XvueState::green[i],
            XvueState::blue[i]);
        XvueState::palette_cache_dirty_[i] = false;
    }
    st->foreground_ = XvueState::palette_cache_[i];
    st->applyPen();
}
```
