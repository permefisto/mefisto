# Phase 03.1 — Operator notes for the 03-04 A/B human gate

**Audience:** the human operator running `/gsd-execute-plan 03-04`
Task 2 (the xvtest1..4 Qt-vs-X11 side-by-side visual comparison).

**Purpose:** pre-document accepted behavioral divergences between
the legacy X11 and Qt backends so they are NOT flagged as regressions.

## xvtest1 font enumeration — KNOWN ACCEPTED DIVERGENCE

`prpr/xvtest1.f` lines 43-57 loop over `I = 1, 32` and call
`CHARGEFONTE(50 + I)` — loading 32 sequentially-numbered X server
fonts and then rendering a single line of text in each. On the legacy
X11 backend this exercises the ~512-font-index-space the X server
exposes (see `xvue/xvinit.f:84-86` — caller passes the PARAMETER
`MAXFONTS=512` from `incl/xvfontes.inc`).

**The Qt backend does NOT reproduce this.** Phase 3 D-04 (see
`.planning/phases/03-text-fonts-colormap/03-CONTEXT.md`) deliberately
replaced runtime X font discovery with 10 bundled DejaVu Sans Mono
sizes for reproducibility. The Qt `xvchargefonte_` body clamps
`*nofont` to `[0, kNbFonts-1] = [0, 9]`. All 32 iterations of the
xvtest1 loop therefore resolve to one of the 10 DejaVu Sans Mono
sizes on the Qt backend.

**Visual expectation:**
- **X11 run of xvtest1:** 32 rows of text, each in a distinct X11
  server font (different families, sizes, weights).
- **Qt run of xvtest1:** 32 rows of text, all in DejaVu Sans Mono
  (10 sizes cycled through the clamp).

**Do NOT flag this as a regression in the D-27 rubric.** This is a
designed-in Phase 3 D-04 behavior change. The acceptance criterion
for xvtest1 is:

- All 32 rows are present (no missing geometry) — CHECK
- All 32 rows contain readable text (not garbled) — CHECK
- Font rendering is consistent within each row — CHECK
- Font *family* matches X11 row-by-row — **WAIVED** per D-04

If the operator observes 32 identical DejaVu rows on Qt and 32
distinct server-font rows on X11, that is the **expected** outcome
and the driver passes.

## xvtest1 STOP path (Pitfall 3)

If the Qt run of xvtest1 prints `PROBLEME AVEC LA SOURIS` and exits
immediately, this means Phase 5 is still not delivered (xvsouris_ is
a stub returning `NOTYEV = 0`). xvtest1 lines 163-165 check `IF
NOTYEV .EQ. 0 THEN; PRINT 'PROBLEME AVEC LA SOURIS'; STOP; ENDIF`.
`STOP` exits 0 on gfortran — so the headless smoke reports green,
but the operator should be aware that the driver aborted early and
did not exercise the full scene. This is expected until Phase 5
lands.

However, in the Phase 03.1 Plan 03 Wave 2 headless smoke run we
actually observed xvtest1_qt reaching end-of-main (repeated `ENTRER
UN CARACTERE POUR FINIR` prompts) and blocking on stdin until the
5 s timeout fired (SIGTERM, exit 143). The STOP path is therefore
NOT hit on this host — the test runs the full scene. Both outcomes
are acceptable.

## xvtest2/3/4 GOTO 100 infinite loop (Pitfall 4)

Same Phase 5 dependency. `xvtest2.f:85-95`, `xvtest3.f:150-158`,
`xvtest4.f:65-70` all contain:

```fortran
 100  CALL XVSOURIS( NOTYEV, NC, NPX, NPY )
      IF( NOTYEV .NE. 2 ) GOTO 100
```

With the Qt stub returning `NOTYEV = 0` forever, these loop until
killed. The 03-04 Task 1 smoke harness wraps each run in `timeout
--preserve-status 5s`, which kills the process with SIGTERM on
timeout — Bash then reports exit code **143**, not 124.

**Exit code tolerance for the 03-04 smoke harness:** accept **0**
(natural exit, e.g. xvtest1 STOP path), **124** (plain `timeout`
without `--preserve-status`, kept for backwards compatibility), or
**143** (SIGTERM via `timeout --preserve-status`, the actual observed
value on this host).

## xvinfo_ MAXFONTS pointer-write crash (fixed in this plan)

**Observed during Wave 2 smoke of xvtest1_qt:** SIGSEGV in `xvinfo_`
called from `xvinit_` called from `xvouvrir_`, first stack frame in
the Fortran main program.

**Root cause:** The Qt backend's `xvinfo_` body was writing `*maxfonts
= nfonts` as a courtesy return value. But `xvue/xvinit.f:84-86` and
`xvue/xvpxfe.f:65` pass the Fortran PARAMETER constant `MAXFONTS`
(defined in `incl/xvfontes.inc`). With gfortran `-O` (the default in
`bin/cbxvtest*_qt`), PARAMETER-sourced actual arguments can land in
read-only memory, and writing through the pointer segfaults on the
first caller that exercises the `XVOUVRIR → XVINIT → XVINFO` chain
(that is the first time any Qt driver reaches this code path — ppxvtest0_qt
uses `XVINITGRAPHIQUE` directly and bypasses `xvinit.f`, which is why
the bug was not caught in Plan 01).

**Fix:** Removed the `*maxfonts = nfonts` write. The legacy C backend
(`xvue/xvuelc.c:612-1042`) never writes `*maxfonts` — it is a pure
input/capacity parameter. The Qt implementation now matches that
contract. `*nbfonts` remains the authoritative "number of fonts
populated" return.

**File touched:** `xvue/qt/src/xvue_qt_api.cpp` (xvinfo_ body,
6-line removal + 10-line comment block). BUILD-07 X11 bit-identity
preserved — `xvue/xvuelc.c` and `xvue/xvouvrir.f` were NOT modified.
ABI count unchanged: `verify_abi: nm count: 57  header count: 57`.

## Legacy X11 xvtest{0,1} pre-existing crashes

Phase 03.1 Plan 02 Pitfall 6 closed: `bin/cbxvtest0` legacy was
previously missing. Plan 03 Wave 2 is therefore the FIRST time the
legacy X11 variants of xvtest0 and xvtest1 have ever been linked and
run.

**Both crash at startup** with pre-existing bugs in the legacy
`xvue/xvuelc.c`:

- `pp/ppxvtest0`: SIGSEGV in `xvtypetrait_` (`xvue/xvuelc.c:1784` —
  `XChangeGC(display_mef, ...)` against a null/unconfigured GC).
  Probable lifecycle-order violation where xvtest0.f calls
  XVINITGRAPHIQUE then XVTYPETRAIT directly, bypassing the XVOUVRIR
  → XVINIT path that the legacy backend expects.

- `pp/ppxvtest1`: SIGSEGV in `xvnbpixeltexte_`
  (`xvue/xvuelc.c:1596` — font metric query). Probable NULL
  XFontStruct returned from one of the 32 sequential `CHARGEFONTE`
  calls, since the X server's font index space has drifted since
  the 1995 authorship of the test.

**These are out-of-scope for Phase 03.1.** Phase 03.1 does NOT
modify `xvue/xvuelc.c`. They are documented in
`deferred-items.md` for a future legacy-backend hardening pass.

**Operator impact on 03-04 Task 2:** the xvtest0 and xvtest1 legacy
A/B side-by-side will NOT work — the legacy binary crashes before
drawing anything visible. Operator should compare xvtest{2,3,4}
legacy vs Qt visually, and mark xvtest0/xvtest1 legacy as "crash,
pre-existing, see 03.1-NOTES.md + deferred-items.md".
