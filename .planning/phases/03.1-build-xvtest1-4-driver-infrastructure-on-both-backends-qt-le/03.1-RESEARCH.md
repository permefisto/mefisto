# Phase 03.1: Build xvtest1..4 driver infrastructure on both backends — Research

**Researched:** 2026-04-11
**Domain:** Fortran 77 build wiring, Qt 6 ABI gap analysis, legacy X11 parity
**Confidence:** HIGH (all claims verified by direct codebase inspection and live binary runs)

## Summary

Phase 03.1 was inserted as a mechanical "wire up 4 missing build scripts" phase, but
direct inspection shows the work is **partly mechanical and partly a Phase 1 leftover**.
The build wiring itself is trivially analogous to the working `bin/cbxvtest0_qt` template
[VERIFIED: bin/cbxvtest0_qt], but there is a **latent behavioral blocker** for the Qt
backend: every one of `prpr/xvtest{1,2,3,4}.f` opens its window through `CALL XVOUVRIR`,
which in turn calls `CALL XTINIT` (xvue/xvouvrir.f:12) — and `xtinit_` in the current
Qt backend is still a warn-once stub
[VERIFIED: xvue/qt/src/xvue_qt_api.cpp:174-180, grep output]. By contrast,
`prpr/xvtest0.f` bypasses the problem entirely by calling `XVINITGRAPHIQUE` directly
(xvtest0.f:36,144) [VERIFIED]. So building and linking the 4 drivers will succeed, but
running them offscreen on the Qt backend will skip all window creation and the
subsequent `XVMMECRAN → XVPXECRAN → XVINFO → XVPXFENETRE → XVRECUPRGBDEC → EFFACER →
CHOIXFONTE → XVEPAISSEUR → XVTYPETRAIT` chain in `xvue/xvinit.f` will run against a
null `XvueWindow` / null backing pixmap.

Separately, **all Fortran-wrapper calls** xvtest1..4 make (`PALCDE`, `CHOIXFONTE`,
`CHARGEFONTE`, `ISOFENETRE`, `AXONOMETRIE`, `FACE2D`/`3D`, `TRAIT2D`/`3D`,
`TEXTE2D`/`3D`, `SYMBOLE2D`/`3D`, `ENTIER2D`/`3D`, `REEL2D`/`3D`, `NUPXEX`,
`NUPXEY`, `PTVLONLAT`, `XYZAXO`, `MEMPXFENETRE`, `EFFACE`) are present in
`xvue/lib` as Fortran-77 subroutines [VERIFIED: `nm xvue/lib | grep T`]. They
all eventually funnel down to the 34 public C entry points in `libxvueqt.a`, all
of which xvtest1..4 transitively use (or will warn-once on and continue).

**Primary recommendation:** Treat Phase 03.1 as **three work streams**, not one:
(1) add 4 + 4 build scripts and wire both top-level builds (30-line shell edits);
(2) promote `xtinit_` from warn-once stub to a functional forward to
`xvinitgraphique_` (≈5 lines in `xvue/qt/src/xvue_qt_api.cpp`) — alternatively
patch `xvue/xvouvrir.f` to also call `XVINITGRAPHIQUE` after `XTINIT` (safer,
affects both backends identically); (3) headless smoke each driver and quiet
any newly exposed warn-once stubs for entries used by xvtest1..4 that the Qt
backend has not yet implemented (see Pitfalls §1). The legacy X11 build path
has no script for `xvtest0..4` at all — four fresh `cb*` scripts are needed
there too, linking against `xvue/xvuelc.o` + `-lX11 -lXext` patterns copied
from `bin/cbmail` (not `bin/cbmail_qt`).

## Architecture Patterns

### Recommended pattern: Mirror `bin/cbxvtest0_qt` exactly × 4

```bash
# bin/cbxvtest1_qt — identical to bin/cbxvtest0_qt except nompp + source
nompp=pp/ppxvtest1_qt
gfortran -Wall -mcmodel=large -m64 -O -fopenmp -I. prpr/xvtest1.f \
    util/lib xvue/lib \
    -Lxvue/qt/build -lxvueqt $QT_LIBS -lstdc++ \
    -lgfortran -o $nompp
```

**Why this link order matters** [VERIFIED: `bin/cbxvtest0_qt:39-42`, `bin/cbelas_qt:40-43`]:
1. `prpr/xvtest1.f` first — the `.f` source is compiled to `.o` and driven into the link
2. `util/lib` — general-purpose Fortran utilities
3. `xvue/lib` — Fortran wrappers (`XVOUVRIR`, `XVINIT`, `CHOIXFONTE`, `FACE2D`, etc.)
4. `-Lxvue/qt/build -lxvueqt` — C++ backend library with the 34 `extern "C"` symbols
5. `$QT_LIBS` — `Qt6Widgets Qt6Gui Qt6Core Qt6PrintSupport` via pkg-config
6. `-lstdc++` — C++ runtime
7. `-lgfortran` — Fortran runtime (must be last because libxvueqt.a's C++ calls into gfortran's I/O for PRINT statements from Fortran callbacks — not applicable here, but maintained for parity with `cbelas_qt`)

Deviations from this order will produce link errors for Qt symbols or Fortran runtime.

### Recommended pattern: Legacy X11 link — mirror `bin/cbmail` (or `cbelas`), NOT `cbmail_qt`

[VERIFIED: bin/cbl_tout:50 calls `bin/ccxvue`] The legacy path builds `xvue/xvuelc.o`
via `bin/ccxvue` (which compiles `xvue/xvuelc.c` with `-I/usr/X11R6/include`) and
then expects every legacy `pp/pp*` executable to link `xvue/xvuelc.o` + `-L/usr/X11R6/lib64
-lX11 -lXext`. The Phase 03.1 legacy scripts must follow this same pattern. Read
`bin/cbmail` (NOT `cbmail_qt`) as the canonical template before writing
`cbxvtest{0..4}`. The Qt template uses `-lxvueqt + Qt libs` and **must not be
mixed** with the legacy path.

### Anti-patterns to avoid

- **Do NOT create one omnibus `bin/cbxvtests` script** that builds all four. The
  project convention is one script per executable (`cbmail`, `cbelas`, `cbflui`,
  ...). A single script violates the existing discipline and makes `bin/cbl_tout`
  integration harder.
- **Do NOT link `xvuelc.o` into the `_qt` drivers**. `libxvueqt.a` is the sole
  graphics backend for the Qt path. Mixing them will produce duplicate-symbol
  link errors on `xvinitgraphique_`, `xvouvrir_`, etc.
- **Do NOT rely on `make` or CMake for the Fortran drivers**. The project has
  a shell-script build system — all `bin/cb*` scripts are invoked directly.
  CMake's scope is strictly `xvue/qt/` (libxvueqt.a only) per an Init-phase
  decision [VERIFIED: STATE.md:69 "Init: CMake owns only `xvue/`; Fortran
  shell build stays unchanged"].

## Common Pitfalls

### Pitfall 1: `xtinit_` is a stub and `XVOUVRIR` depends on it

**What goes wrong:** `bin/cbxvtest{1..4}_qt` link cleanly and `pp/ppxvtest1_qt`
starts, but the first warn-once line is `xvue-qt: xtinit_ not implemented` and
no window ever opens. Subsequent calls (`XVMMECRAN`, `XVPXECRAN`, `XVINFO`, ...)
run without a backing window. They don't crash because every Phase 1/2/3 entry
point begins with `XvueApp::ensure()` which creates the QApplication — but no
`XvueWindow` exists, so `XvueWindow::current()` returns null and every drawing
entry takes its null-guard early-return path. The Qt driver exits 0 (so a naive
smoke test passes), produces no visible output, and the plan 03-04 Task 1
warn-once grep does NOT catch `xtinit_` because the grep pattern is
`(xvchargefonte|xvnbpixeltexte|xvtexte|xvftexte|xvcouleur|xvrecuprgbdec|xvactivervb)`
[VERIFIED: 03-04-PLAN.md:111-113] — `xtinit_` is not in the list.

**Why it happens:** `xvue/xvouvrir.f:12` calls `CALL XTINIT` before `CALL XVINIT`.
The legacy `xvuelc.c` implementation of `xtinit_` is what actually opens the
X toolkit + maps the window. The Qt backend's `xtinit_` was left as a no-op
because Phase 1 used `xvinitgraphique_` as the window-open path. But
`prpr/xvtest0.f` calls `XVINITGRAPHIQUE` directly (lines 36, 144), bypassing
`XVOUVRIR`, so Phase 1/2/3 never exercised the `XVOUVRIR → XTINIT` path.
`prpr/xvtest{1,2,3,4}.f` ALL open via `CALL XVOUVRIR`, so they're the first
driver code that hits the gap. [VERIFIED: Grep of both patterns in all 5 files]

**How to avoid:** Patch either:
- **(Recommended) `xvue/xvouvrir.f`** — add `CALL XVINITGRAPHIQUE` between
  lines 12 and 14 (before `CALL XVINIT`). This affects both backends: on X11
  it's a call-through that the xvuelc.c body already handles; on Qt it opens
  the window via the Phase 1 real body. Safer because the Fortran wrapper is
  the natural scope-boundary.
- **(Alternative) `xvue/qt/src/xvue_qt_api.cpp` `proc(xtinit)`** — replace the
  warn-once stub body with `proc(xvinitgraphique)(void); return;`. This also
  works but introduces a Qt-only asymmetry — the legacy `xtinit_` still does its
  own window open, while the Qt `xtinit_` aliases to `xvinitgraphique_`.

**Warning signs:** `ppxvtest1_qt` starts quickly and exits immediately; stdout
shows the INITIER banner but no `Fonte 51`/etc. progress lines from xvtest1's
DO 10 loop, or the loop runs but `XVNBPIXELTEXTE` returns 0/0 for every line.

**Decision required:** Which patch path? Recommend the Fortran-side patch as
D-01 for this phase. Alternative: ask the user during `/gsd-discuss-phase`.

### Pitfall 2: `CHARGEFONTE(NF)` with NF = 51..82 will clamp to DejaVu Sans Mono 32pt

**What goes wrong:** `prpr/xvtest1.f:44-57` loops `I=1,32` and calls
`CHARGEFONTE(50+I)` — loading 32 different fonts sequentially. The legacy X11
backend treated this as "font index into the X server's list of ~512 fonts"
[VERIFIED: xvue/xvinit.f:212 `NBFONT .LE. 0 .OR. NBFONT .GT. 512 NBFONT=512`].
The Qt backend has `kNbFonts = 10` and clamps `*nofont` to `[0, kNbFonts-1]`
[VERIFIED: 03-02-SUMMARY.md:52]. So all 32 iterations will load the 10th bundled
DejaVu font size, and the visual A/B will look dramatically different — the
legacy backend shows 32 distinct font styles, the Qt backend shows 32 identical
lines in DejaVu Sans Mono 32pt (and whatever 22 clamp-redundant calls amount to).

**Why it happens:** Phase 3 deliberately rejected runtime X font discovery in
favor of 10 bundled DejaVu sizes per D-04 (bundling reproducibility). The A/B
rubric in `03-CONTEXT.md:D-27` accepts "subpixel differences in glyph shape"
but does NOT explicitly accept "font-family difference."

**How to avoid:** This is a **known behavior divergence** and cannot be fixed
in Phase 03.1 without reopening Phase 3 decisions. Document it in the phase
CONTEXT as an expected A/B divergence for the xvtest1 driver specifically:
"xvtest1 font-enumeration loop is a legacy X11 feature that Phase 3 deliberately
replaced with a fixed 10-size bundled font." The Task 2 human operator in plan
03-04 will see this and should not flag it as a regression. Recommend adding a
note to `03-04-PLAN.md` OR producing a `phase-03.1/NOTES.md` file the A/B operator
reads before running xvtest1. Consider filing as a deferred D-xx decision.

**Warning signs:** xvtest1's 32 font lines all look identical on Qt, different
on X11. If the operator reports this as a failure, escalate to "expected
divergence per Phase 3 D-04."

### Pitfall 3: `XVSOURIS` blocking is the only way xvtest1..4 return control

**What goes wrong:** Every one of xvtest1..4 calls `XVSOURIS` at least once.
In xvtest1 there are multiple loops: "CLIC SOURIS POUR AVOIR LA PALETTE DE
COULEURS 1..14" (14 consecutive click waits). The driver cannot exit 0 under
`QT_QPA_PLATFORM=offscreen` without user input. **But it DOES exit 0** on the
Qt backend because Phase 5 is not done — `xvsouris_` is still a warn-once stub,
returns immediately with `NOTYEV = 0` [VERIFIED: xvue/qt/src/xvue_qt_api.cpp —
grep shows xvsouris_ in warn-once table via its stub status]. In xvtest1 that
triggers `IF( NOTYEV .EQ. 0 ) THEN; PRINT 'PROBLEME AVEC LA SOURIS'; STOP; ENDIF`
at line 163-165 — the program prints "PROBLEME AVEC LA SOURIS" and exits with
`STOP` (exit code 0 on gfortran).

**Why it happens:** `STOP` without a numeric code exits 0 on gfortran. So the
smoke test passes (exit 0) even though the driver took the error path. Plan
03-04 Task 1's grep pattern doesn't include `'PROBLEME AVEC LA SOURIS'` or
`'stop'`, so the smoke will report GREEN on a functionally-aborted run.

**How to avoid:** Extend plan 03-04 Task 1's acceptance grep to include
`'PROBLEME AVEC LA SOURIS'` (xvtest1), `'PAS D''EVENEMENT'` (xvtest2/3/4 via
their `IF NOTYEV .NE. 2 GOTO 100` loops which will spin forever — see Pitfall 4).
The Phase 03.1 plan should establish a richer smoke grep that catches all
"Phase 5 is missing" early-exit paths, not just Phase 3 warn-once lines.

**Warning signs:** `ppxvtest1_qt` exits almost instantly (< 100ms instead of
the expected 5-10 seconds); stdout contains `PROBLEME AVEC LA SOURIS`.

### Pitfall 4: `xvtest2..4` infinite-loop on `GOTO 100` when xvsouris_ is a stub

**What goes wrong:** xvtest2 (line 90-93), xvtest3 (155-158), xvtest4 (67-70)
all have:
```fortran
 100  PRINT *
      PRINT *,'ENTRER UN CARACTERE POUR FINIR'
      CALL XVSOURIS( NOTYEV, NC, NPX, NPY )
      IF( NOTYEV .NE. 2 ) GOTO 100
```
With the Qt stub returning `NOTYEV = 0` forever, this becomes an infinite loop
printing "ENTRER UN CARACTERE POUR FINIR" to stdout at maximum speed. The
2-second `kill` in plan 03-04 Task 1 was designed for legacy X11 drivers that
BLOCK on XSelectInput — it is not appropriate for the Qt drivers, which will
spin not block.

**Why it happens:** Same root cause as Pitfall 3 — Phase 5 deferred `xvsouris_`.

**How to avoid:** Add a `timeout 5s` wrapper to every Qt smoke in Task 1:
```bash
timeout --preserve-status 5s pp/ppxvtest${N}_qt ...
```
or wrap with a sentinel output size check (kill if `/tmp/03-04-*.out` grows
past 100 KB). Recommend `timeout 5s` — simpler and already a coreutils tool.
Exit code of `timeout` is 124 on timeout, 0 on natural exit, non-zero on crash.
Adjust the acceptance rule to accept `0 OR 124` and require **no** crash markers
in the captured stdout.

**Warning signs:** `/tmp/03-04-xvtest2-qt.out` is hundreds of KB, dominated by
repeated `ENTRER UN CARACTERE POUR FINIR` lines.

### Pitfall 5: `xvtest{1,2,3}.f` emit PostScript files to current working directory

**What goes wrong:** `CALL XVSAUVERPS('XVUEtest1', 9)` (xvtest1:215),
`XVSAUVERPS('XVUEtest3.1', 11)` ... through 3.5 (xvtest3), and two other
similar calls will, in the legacy backend, write `XVUEtest1.ps`/`XVUEtest3.1.ps`/
... into whatever `$PWD` was at launch. The Qt backend's `xvsauverps_` is a
warn-once stub (not in the TEXT set, so Task 1 grep won't flag it), so no file
is written. However, if Phase 7 is ever back-ported, PS files will start landing
in `$MEFISTO/` and polluting git status.

**Why it happens:** Phase 7 is post-Phase 6. `xvsauverps_`/`xvimprimerps_`/
`xvinitierps_` are deliberate warn-once stubs today.

**How to avoid:** Document the expected warn-once set explicitly in the phase
plan: Phase 03.1 smoke accepts warn-once lines for
`{xtinit, xvsouris, xvsouris2, deplsouris, xvpause, xvinitierps, xvsauverps, xvimprimerps,
fenetremempx, sauvefenetre, restaurefenetre, sauvemempx, restauremempx, effacemempx,
initaccrochage}` — these are **Phase 4/5/7 deliverables**, not regressions. The
plan should grep ONLY for warn-once lines NOT in that list.

**Warning signs:** The `/tmp/*-qt.out` file contains warn-once lines the plan
didn't anticipate — they may or may not be regressions.

### Pitfall 6: `bin/cbl_tout` legacy has no `cbxvtest0`, only `_qt` does

**What goes wrong:** Phase 1 added `bin/cbxvtest0_qt` [VERIFIED: commit 4f23477]
but no matching `bin/cbxvtest0` legacy script was ever created. The initial
MEFISTO commit `77d7763` brought `prpr/xvtest0.f..xvtest4.f` as sources but no
build scripts [VERIFIED: `git log --all --follow bin/cbxvtest0` returns zero
results]. So the baseline for Phase 03.1 is **"zero legacy xvtest build scripts
exist; one Qt xvtest build script exists (for xvtest0 only)."** This means
Phase 03.1 actually needs to create **5 legacy scripts** (`cbxvtest0..4`) and
**4 Qt scripts** (`cbxvtest1..4`), plus one-liner additions to both top-level
drivers — 9 new files, 2 edits.

**Why it happens:** The drivers predate the migration. They were built
manually out-of-band in the 1995 era and never made it into the shell scripts.

**How to avoid:** Create `bin/cbxvtest0` to parallel `bin/cbxvtest0_qt` for
BUILD-07 symmetry, even though xvtest0 is a migration-era driver that didn't
exist in 1995. Use `bin/cbmail` as the legacy template (not `cbmail_qt`).

**Warning signs:** `pp/` contains `ppxvtest0_qt` but no `ppxvtest0` when
Phase 03.1 is claimed complete.

### Pitfall 7: `XVFACE(MAXPTS, XPOINTS)` passes INTEGER*2 points at Fortran side

**What goes wrong:** `prpr/xvtest1.f:17-18` declares
`PARAMETER (MAXPTS=50); INTEGER*2 XPOINTS(2,MAXPTS)` and then passes
`XPOINTS` to `XVFACE`. The Qt ABI signature is
`void xvface_(int *n, MefistoPoint *pts)` where
`MefistoPoint = { short x; short y; }` [VERIFIED: xvue_qt_api.h:33].
This is byte-identical to `INTEGER*2 (2,MAXPTS)` — so the call works. Phase 2
verified this already with `xvtest0` (which also uses `INTEGER*2 PTS(2,8)`).

**Why it might still bite:** The Fortran-to-C layout assumes `sizeof(short)==2`
on the target, which is true everywhere MEFISTO runs, but `static_assert` in
the header already enforces it [VERIFIED: xvue_qt_api.h:34-35 `sizeof(MefistoPoint) == 4`].
NO fix needed — calling this out so the planner doesn't second-guess it.

**How to avoid:** Don't touch `INTEGER*2 XPOINTS` declarations in xvtest1.
The layout is already correct by design.
