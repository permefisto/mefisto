# Phase 06.4: Code Review Report

**Reviewed:** 2026-04-28T00:00:00Z
**Depth:** standard
**Files Reviewed:** 14
**Status:** issues_found

## Summary

Phase 6.4 ports the thermal-solver menu wiring (the 4th iteration after mail / elas / flui), adding a `Thermal` top-level QMenu, 7 new SVG icons, a strong-symbol override of `registerTherActions_stub_`, force-link keepalive in `xvue_qt_app.cpp`, qrc registrations, and a 7-slot QTest binary that codifies all 6.2/6.3 carry-forward gates as automated checks. The code closely mirrors the 6.3 flui template and reads as a clean port. The shared idioms (one-shot guard, ensureTopLevelMenu(insertBefore=...), Q_ASSERT_X on viewMenuForAnchor, [menu]-echo-then-queue, force-link keepalive) are all correctly carried over. Bilingual menu data files all exist under `td/ma/`, ABI-symbol filtering is intact, and the ther-specific `98;` Help allowlist (vs. flui's `97;`) is correctly threaded through both Plan 02 wiring and Plan 03 test allowlist.

One genuine semantic mismatch was found: under the `View > Draw temperatures + flux` (`8;`) submenu, the four `tempgrad` leaves are wired with the `7;` (eigenvector drawing) prefix instead of `8;` — this means clicking "Numero du cas" under the temperature menu actually triggers the eigenvector drawing dispatcher rather than the temperature dispatcher (both end up in `TRTHER`, but with different `NTYPDESS` arg). The remaining items are documentation drift (stale ABI comment, comment typos, line-number off-by-3) plus two intentional but worth-noting design choices (DEAD-CODE wiring of code `19;`, missing optional leaves for `scheonde.label(2)` / `resothst.label(3)`).

## Warnings

### WR-01: `tempgrad` leaves under `View > Draw temperatures + flux` use `7;` prefix instead of `8;`

**File:** `xvue/qt/src/xvue_qt_ther_actions.cpp:386-394`
**Issue:** The `drawTempMenu` (a child of `viewMenu`, parent leaf lexicon `8;`, label `debuther.label(8)` = "DRAWING of TEMPERATURES and FLUX") contains four leaves wired with lexicons `7;1;`, `7;2;`, `7;3;`, `7;4;`. The other sibling submenus (`tractempMenu`, `tractem1Menu`, `fluxMenu`, `gradMenu`) all correctly use the `8;` prefix (`8;20;1;`, `8;30;1;`, `8;60;1;`, `8;70;1;`).

In `prpr/ppther.f:226`, code `7` and code `8` dispatch to two different `TRTHER` calls (`CALL TRTHER(KNOMOB, 2, IERR)` for eigenvectors at line 361 vs. `CALL TRTHER(KNOMOB, 1, IERR)` for temperatures at line 367). Both `TRTHER` calls then read `tempgrad` as their next menu — same menu file, different `NTYPDESS` argument controlling what gets drawn. The lexicon prefix matters: a user who clicks "Numero du cas" inside the *Draw temperatures + flux* menu will queue `7;1;`, which dispatches to **eigenvector drawing**, not temperature drawing. The menu label and the rendered output disagree.

The comment on line 386 ("`7;1; .. 7;4; -- tempgrad leaves (canonical drawing dispatcher)`") describes the eigenvector path while the surrounding `drawTempMenu` is labeled and iconified for temperatures — strong evidence this is an unintentional copy-paste from a different audit row, not a deliberate UX choice.

**Fix:** Change the four leaf lexicons to use the `8;` prefix:
```cpp
        // 8;1; .. 8;4; -- tempgrad leaves (canonical drawing dispatcher
        // entered through the temperature TRTHER call at ppther.f:367)
        drawTempMenu->addAction(makeLeafAction(win, mb,
            tempgrad.label(1), QStringLiteral("8;1;")));
        drawTempMenu->addAction(makeLeafAction(win, mb,
            tempgrad.label(2), QStringLiteral("8;2;")));
        drawTempMenu->addAction(makeLeafAction(win, mb,
            tempgrad.label(3), QStringLiteral("8;3;")));
        drawTempMenu->addAction(makeLeafAction(win, mb,
            tempgrad.label(4), QStringLiteral("8;4;")));
```
If the audit deliberately chose `7;` (because the same menu-tree is reused for eigenvectors and the user is expected to read `tempgrad` regardless of entry path), then the `drawTempMenu` heading or the leaf labels need to reflect that — the current naming makes the path opaque. Recommend confirming against `LEXICON-AUDIT-ther.md` row 8 before patching.

## Info

### IN-01: Stale ABI count comment in CMakeLists.txt contradicts active enforcement

**File:** `xvue/qt/CMakeLists.txt:95`
**Issue:** The comment reads `# Expected count after Option A resolution of Planner Alert: 57.` but `xvue/qt/cmake/verify_abi.sh:45` enforces `if [ "$NM_COUNT" != "58" ]` and emits a warning otherwise (Phase 6.0 added `xvue_module_init_`, taking the count from 57 → 58). The comment is from before Phase 6.0 landed.
**Fix:** Update the comment to reflect the current invariant:
```cmake
# Expected count after Phase 6.0 added xvue_module_init_: 58.
# Per-module register<Mod>Actions_stub_ symbols are filtered out by
# verify_abi.sh so 6.1..6.5 do not bump this count.
```

### IN-02: Test-file docstring references nonexistent `Thermal.HeatSteady` objectName

**File:** `xvue/qt/tests/test_xvue_qt_ther_menu.cpp:42-45`
**Issue:** The class-level header comment states `actionByLexicon walks submenus so "3;" (inside Thermal.HeatSteady or directly in Thermal) ...`. The actual objectName set in `xvue_qt_ther_actions.cpp:275` is `"Thermal.Steady"`, not `"Thermal.HeatSteady"`. The mismatch is comment-only — `actionByLexicon` walks by `QMenu::actions()` recursion and never compares object names — but the doc reads as if grepping the source for `Thermal.HeatSteady` would find a match.
**Fix:** Replace `Thermal.HeatSteady` with `Thermal.Steady` in the comment.

### IN-03: Action-file docstring cites wrong line number for the dead `THEPOLEVV` call

**File:** `xvue/qt/src/xvue_qt_ther_actions.cpp:18, 339`
**Issue:** Two comments reference `ppther.f:451` for the dead `THEPOLEVV` dispatch. The actual commented-out call at the time of review is on `ppther.f:454` (`ccc      CALL THEPOLEVV( KNOMOB, NBJEUX, IERR )`). The label `1900` itself starts at `ppther.f:453`, not 451.
**Fix:** Update both references to `ppther.f:454` (or the label-relative form `ppther.f:1900` which is more robust against unrelated edits).

### IN-04: `scheonde.label(2)` not wired despite both menu-file leaves being available

**File:** `xvue/qt/src/xvue_qt_ther_actions.cpp:323-325`
**Issue:** The Wave submenu wires only `5;81;1;` (Newmark implicit). `td/ma/scheonde` exposes two qaction-eligible codes — code 1 (Newmark) and code 2 (Implicit DECENTRED). Phase 6.3's flui Stokes submenu wired both `methrecr.label(1)` and `methrecr.label(2)` for symmetry. If the audit deliberately gates code 2 as `qaction=no`, the audit comment should be reproduced inline; otherwise the leaf is missing.
**Fix:** Either add the second leaf:
```cpp
    waveMenu->addAction(makeLeafAction(win, mb,
        scheonde.label(2), QStringLiteral("5;81;2;")));
```
or annotate the omission with a one-line "audit-gates code 2 because ..." comment.

### IN-05: Code `19;` (POLY EIGEN) wired to a runtime no-op

**File:** `xvue/qt/src/xvue_qt_ther_actions.cpp:338-344`
**Issue:** The leaf for `19;` queues a lexicon that, on the Fortran side, dispatches to label `1900` whose only active line is `IF( NBPAS .EQ. 0 ) GOTO 100` followed by `GOTO 30` — the `CALL THEPOLEVV` is commented out (`ppther.f:454`). Triggering the menu item silently consumes input and returns to the prompt with no user-visible effect. The comment ("Wired for menu completeness; user clicks fire the lexicon but the Fortran side is a no-op") acknowledges this. Decision is intentional, but the menu item should at minimum be visually distinguished (greyed-out or "(disabled)" suffix) so users do not perceive the silent-noop as a bug.
**Fix:** Optional — call `a->setEnabled(false)` for this specific leaf, or annotate the label with a `(stub)` suffix; alternatively, gate the registration behind a `#if 0` block matching the Fortran `ccc` comment so the two stay in sync.

### IN-06: Source comment block (line 36) in `prpr/ppther.f` references the wrong load module

**File:** `prpr/ppther.f:36`
**Issue:** The block comment reads `C     LES ARGUMENTS A L'APPEL DU LOAD MODULE ppflui` despite this file being `ppther.f`. This is a pre-existing copy-paste from `prpr/ppflui.f:41` and not introduced by Phase 6.4 (the surrounding `XVUE_MODULE_INIT('ther', 4)` line is the only 6.4 change in this file). Flagging because the file is in scope for the review and the comment will mislead future readers grepping for module-specific argument handling.
**Fix:** Replace `ppflui` with `ppther`:
```fortran
C     LES ARGUMENTS A L'APPEL DU LOAD MODULE ppther
```
