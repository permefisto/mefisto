# Phase 6.1: Mesher (mail) menu wiring - Context

**Gathered:** 2026-04-20
**Status:** Ready for planning

<domain>
## Phase Boundary

`ppmail_qt` shows a fully-populated mesher menu bar (`{File, Mesh, View, Help}`),
a toolbar with the top-5 most-used leaf commands, and executes
`CALL XVUE_MODULE_INIT('mail')` at startup. Approximately 30 `QAction`s cover
the 80 % most-used leaf commands of `mail/`; every leaf action pushes its full
typed-lexicon path (e.g. `1;1;` for *Create Point*) via
`XvueMenuBridge::queueLexicon`. The typed lexicon remains fully functional and
unchanged for every command, GUI-surfaced or not — clicks and keystrokes are
interchangeable at every step.

**Invariant (from Phase 6.0 D-03):** zero changes to Fortran solver drivers
besides the single `CALL XVUE_MODULE_INIT('mail')` line in `prpr/ppmail.f`.
The typed lexicon is always the always-available fallback — this phase is
additive UX, not a replacement.

</domain>

<decisions>
## Implementation Decisions

### Top-level menu taxonomy
- **D-01:** Top-level menu bar for `ppmail_qt` is `{File, Mesh, View, Help}`.
  **Edit is dropped** — its candidate items were mesh parameters rather than
  text-editing operations, so Edit would be semantically empty. This is a
  deliberate deviation from ROADMAP.md §Phase 6.1 which listed
  `{File, Edit, Mesh, View, Help}`; the roadmap wording is updated at plan
  time.

### File menu contents
- **D-02:** File menu wraps process-level / storage operations from `debut`:
  - `99;` *Save & Quit* (also bound to `File → Quit` and to the window close
    button — see D-09)
  - `80;` *Import a PLSVO mesh*
  - `90;` *Export a PLSVO mesh*
  - `70;` *Manage Mefisto TMS file units* (memory-secondaire) — File menu
    because TMS files ARE the mesh-data storage layer in MEFISTO's model
  - Shared 6.0 actions: *Open Project…*, *Save Project*, *Save Project As…*,
    *Export…*, *Recent Projects* submenu (10 max, D-06 from 6.0), *Preferences*

### Mesh menu contents
- **D-03:** Mesh menu holds the geometry actions at the top level and mesh
  parameters in a **Parameters submenu**:
  - Top-level (geometry): `1;` Points, `2;` Lines, `3;` Surfaces, `4;` Volumes,
    `5;` Objects, `6;` Mappings (R³→R³), `7;` Interpolation nodes
  - `Mesh → Parameters` submenu: `0;` Default edge length, `11;` Rename
    edge-length, `20;` Point-identification precision, `21;` Automatic mesh
    update
  - Each top-level geometry entry is itself flat (D-05): e.g.
    `Mesh → Points → Create / Modify / List / Delete / …` with up to 5 leaf
    QActions per category.

### View menu contents
- **D-04:** View menu = display-affecting actions from `debut`:
  - `10;` Draw PLSVO meshes
  - `19;` Min/MAX of XYZ (viewport framing)
  - `60;` Manage the Mefisto graphic window (window-state sub-operations)
  - Shared 6.0 actions: console-dock toggle, canvas reset-view, color-scheme
    sub-menu (auto / light / dark)

### QAction ↔ LIMTCL mapping strategy
- **D-05:** **Flat QActions for leaf commands.** Each action wires directly to
  a specific leaf command — e.g. `Mesh → Points → Create` pushes `1;1;`,
  `File → Import` pushes `80;`, `View → Draw mesh` pushes `10;`. Target ~30
  QActions (middle of the roadmap's 20–40 range). Users can still type any
  command — the two paths are interchangeable at every tree depth. The
  `Mesh → Points` menu header is a QMenu (not a QAction), so hovering it
  does not push anything; only leaf clicks queue lexicon chars.
- **D-06:** **Toolbar holds the top-5 most-used leaf QActions.** Pulled from
  the same ~30-action set, chosen by frequency (D-10). Toolbar icons reuse
  the QAction's icon. Shared 6.0 toolbar actions (Open / Save / About) stay
  on the shared toolbar; mesher-specific icons are appended.

### Lexicon echo on menu clicks
- **D-07:** **Click pushes AND echoes.** When a flat QAction fires, its
  typed-equivalent is echoed to the console dock as `[menu] 1;1;` before the
  chars are queued into `XvueMenuBridge::queueLexicon`. Reason: users learn
  the typed muscle-memory shortcuts by watching them scroll past. Zero runtime
  cost, reinforces the D-04-from-6.0 "typed lexicon is primary" invariant.
  Echo text is bilingual (FR: `[menu] 1;1;`, EN: `[menu] 1;1;` — the numeric
  sequence is identical across languages, only the `[menu]` prefix localises
  as `[menu]` FR and `[menu]` EN — planner may keep it language-neutral).

### Fortran entry hook
- **D-08:** `CALL XVUE_MODULE_INIT('mail')` inserted in `prpr/ppmail.f` after
  `CALL XVINIT` (around line 166) and before the main interactive loop at
  label `90` (line 230). This matches the order documented at
  `xvue/qt/src/xvue_qt_api.cpp:1432` ("*Called once per pp\*_qt process from
  prpr/pp\*.f BEFORE xvinitgraphique_*") — XVUE_MODULE_INIT runs per-module
  setup (color-scheme preference, stdout redirect, register mail actions,
  mark bridge registered, flip canvas has_user_content_). Planner verifies
  exact line placement against the X11 path — pure 6.0 builds (X11) must not
  break.

### File → Quit / window-close semantics
- **D-09:** `File → Quit`, window-X button, and Qt `Q_SHORTCUT(QKeySequence::Quit)`
  all map to pushing `99;` (MEFISTO's *SAVE DATA and QUIT* code), not to
  `QApplication::quit()`. Reason: `99;` routes through Fortran's save path;
  raw `QApplication::quit()` would lose unsaved mesh state. The window's
  `closeEvent` intercepts the close, pushes `99;`, then lets Fortran finish
  its save loop before the process exits. This is the SAME pathway Phase 5
  D-06 uses for Esc=27 / @=64 — reuses the "push char, let Fortran finish"
  pattern.

### LEXICON-AUDIT-mail.md schema
- **D-10:** `LEXICON-AUDIT-mail.md` catalogues every command reachable from
  `td/m*/debut` via **full recursive LIMTCL tree walk** (not just `debut` +
  1 level). Table columns:
  1. `lexicon_path` — full numeric-sequence path, e.g. `1;1;` or `5;2;1;`
  2. `description_fr` — extracted from `td/m/<file>` or `td/mf/<file>`
  3. `description_en` — extracted from `td/ma/<file>`
  4. `frequency` — `high` / `med` / `low`, scored by **draft testa/ counts
     overlaid with user-expert review** (two-pass: planner/auditor produces
     the draft from `grep` + LIMTCL call-site analysis, user reviews and
     adjusts before freeze)
  5. `qaction` — `yes` / `no` (yes iff `frequency` ∈ {high, med})
  6. `toolbar` — `yes` / `no` (top-5 high-frequency leaves)
  7. `icon_source` — Qt `SP_*` enum name (e.g. `SP_DialogSaveButton`) OR
     custom SVG filename (e.g. `mesh-vertex-add.svg`) OR `—` for menu-only
     text
  8. `shortcut` — `Ctrl/Alt/Cmd+X` or `F1`..`F12` if assigned, `—` otherwise
  9. `notes` — free text for clarifications, e.g. "only valid after step 7"
- **D-11:** `LEXICON-AUDIT-mail.md` target size: approximately 100–150 rows
  covering the full tree. 20-row `debut` + typical 5-10 leaves per sub-menu
  over 15–20 reachable sub-files. The `qaction=yes` set is ~30 rows per D-05.

### Bilingual label source (Claude's Discretion)
- **D-12:** QAction labels are pulled at runtime from `td/ma/<menu>` (EN)
  and `td/mf/<menu>` or `td/m/<menu>` (FR) files, parsed by `XvueMenuBridge`
  at module-init time. Rationale: the Fortran menu files are the single
  source of truth for the lexicon; auto-parsing keeps the QAction labels and
  the typed-lexicon prompts in lock-step. Language selection follows
  existing `$MEFISTO/td/m/anglais` flag (UX-08). Fallback if a menu file is
  missing: label = lexicon-path as string (e.g., `"1;1;"`).

### QTest coverage (Claude's Discretion)
- **D-13:** Mesher-specific QTest case lives in
  `xvue/qt/tests/xvue_qt_mail_menu_tests.cpp` (new file, CMake target
  `xvue_qt_mail_menu_tests`). Scope: one round-trip test per menu (File /
  Mesh / View / Help), picking the most representative leaf QAction each
  time (e.g., `Mesh → Points → Create` triggers `1;1;` ⇒ 4 chars ⇒
  `XvueEventBridge::waitForEvent` returns `notypeevent=2` sequence matching
  `'1'`, `';'`, `'1'`, `';'`). 4 tests total, each <= 30 lines. Adequate
  cross-section without explosive maintenance. Success criterion #5 is
  satisfied when all 4 pass under the offscreen QPA.

### Plan wave split (Claude's Discretion)
- **D-14:** Planner will likely split 6.1 into **3 plans**:
  1. `06.1-01-PLAN.md` — LEXICON-AUDIT-mail.md full tree walk + draft
     frequency scoring (testa/ counts) + user review checkpoint before
     freeze
  2. `06.1-02-PLAN.md` — `registerMailActions()` body + custom SVG icon set
     under `xvue/qt/resources/icons/mail/` + `.qrc` registration + bilingual
     label parser (D-12) + `[menu]` echo (D-07)
  3. `06.1-03-PLAN.md` — `CALL XVUE_MODULE_INIT('mail')` in `prpr/ppmail.f`
     + `closeEvent` `99;` handler (D-09) + QTest cases (D-13) + full-suite
     regression sweep
  Final count/shape is planner's call; this is an expected decomposition.

### Claude's Discretion
- Exact `lexicon_path` string format — single-line `1;1;`, space-separated
  `1 ; 1 ;`, or JSON array `[1, 1]` — planner decides at audit time.
- Whether the custom-SVG set lives under `xvue/qt/resources/icons/mail/` or
  a shared `xvue/qt/resources/icons/mesh/` (if 6.2–6.5 will reuse any of the
  geometry icons). Planner surveys solver icon needs and picks.
- How `registerMailActions()` organises its ~30 QAction creations — one
  function per menu (`buildFileMenu`, `buildMeshMenu`, …) or a single table
  walked with a helper lambda. Readability call.
- Whether the toolbar is one `QToolBar` or split (`Mesh ops` vs `Drawing
  ops`).
- Whether `close`-event `99;` dispatch uses a modal confirmation
  ("Save & quit?") or dispatches silently. Default: silent, consistent with
  the typed-lexicon `99;` which also does not confirm.

## Existing Code Insights

### Reusable Assets
- **`XvueMenuBridge::queueLexicon(QString)`** — exactly the API 6.1 needs.
  Takes a string like `"1;1;"`, pushes each char + trailing CR (13). No
  modification needed.
- **`registerMailActions_stub_`** weak symbol in
  `xvue/qt/src/xvue_qt_api.cpp:75` — 6.1 supplies the strong override in a
  new file (`xvue/qt/src/xvue_qt_mail_actions.cpp`). Build-time link order
  ensures the real body wins.
- **`XvueWindow::menuBar()`, `addToolBar()`** — standard Qt methods available
  on the Phase 6.0 `QMainWindow` shell. Mesh menu + toolbar just call
  `menuBar()->addMenu(tr("&Mesh"))` etc.
- **`XvueApp::applyColorSchemePreference()`** — already called by
  `xvue_module_init_`. QActions inherit the palette automatically; no extra
  wiring.
- **`XvueConsoleDock`** — already in 6.0. `[menu] 1;1;` echo (D-07) appends
  to the existing stdout-redirect stream, so no new widget needed.

### Established Patterns
- **Weak-symbol override** for per-module registration (`_stub_` pattern) —
  Phase 6.0 Plan 06. Each pp\*\_qt's main `.cpp` file will link against
  `xvue_qt_mail_actions.o` / `xvue_qt_elas_actions.o` etc. to pull in the
  strong symbol. `xvue_qt_api.cpp` defines the weak fallback.
- **QAction translation via `tr()`** — standard Qt pattern. Bilingual source
  at runtime (D-12) makes the label-parsing step return the already-
  localised string, skipping Qt linguist altogether. Kept simple.
- **Offscreen QPA for tests** — all 6.0 tests run under `QT_QPA_PLATFORM=
  offscreen`. 6.1 mail-menu tests follow the same contract; no GUI display
  required.
- **Per-module `QSettings` group** (6.0 D-07 carry-forward) —
  `XvuePrefs::initialize("mail")` is already called by `xvue_module_init_`;
  6.1 actions read/write under that group if they need persistence (most do
  not — they just push lexicon chars).

### Integration Points
- **`prpr/ppmail.f:166`** — between `CALL XVINIT` and `CALL OUVRMS` (line

- **`xvue/qt/src/xvue_qt_api.cpp:1486`** — `registerMailActions_stub_(wptr,

<specifics>
## Specific Ideas

- **"Can we make flat QActions for leaf commands and also keep the
  text-driven — user can do like he wants"** (user, Area 2). Interpretation:
  clicks and keystrokes are interchangeable at every depth; no path is
  privileged. The `[menu]` echo (D-07) reinforces this by showing the user
  the typed equivalent of what they just clicked.
- **Full recursive audit, not shallow** (user, Area 3). The long tail must
  be catalogued on paper even if it does not reach the GUI. Planner budgets
  for ~100–150 rows in `LEXICON-AUDIT-mail.md`, not 20.
- **High/med/low frequency bucketing** (user) is explicitly preferred over
  numeric scales. Mapping: `high` → QAction + toolbar, `med` → QAction
  menu-only, `low` → typed lexicon only.
- **Fortran-file-driven bilingual labels** (Claude's Discretion, D-12) —
  single source of truth is the `td/m*/` data. Avoids the Qt-linguist
  round-trip.

</specifics>
