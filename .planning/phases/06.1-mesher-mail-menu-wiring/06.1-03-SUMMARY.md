## Decisions Made

### Architectural
- **!GCC$ ATTRIBUTES WEAK on the Fortran stub** — instead of maintaining separate backend-specific Fortran sources, one `xvue/xvmodi.f` serves both. X11 builds link `xvue/lib` alone → weak body runs as a no-op. Qt builds link `xvue/lib` + `libxvueqt.a` → the C++ `xvue_module_init_` strong symbol in the archive displaces the weak body. Mirrors the C-side weak/strong design used by `registerMailActions_stub_`.
- **Force-link keepalive pattern (Rule 3)** — established the idiom for all 6.2–6.5 module-action TUs: each per-module `xvue_qt_<mod>_actions.cpp` must export a keepalive function and `xvue_qt_app.cpp` must reference it. Without this, GNU ld's archive-search policy silently excludes the strong override even though the weak stub exists.
- **closeEvent gate via blockingDepth()** — reuses the existing `BlockingDepthGuard` RAII from Phase 5 D-03 rather than inventing a new sentinel. The test harness also uses the same guard, confirming the production code path end-to-end.

### Semantic / UX
- **Silent 99; dispatch on File→Quit** — matches the typed-lexicon `99;` which never prompts for confirmation. Click-to-Fortran semantics are identical to type-to-Fortran. Rejected the "Save & quit?" dialog alternative because it would diverge the two input paths.
- **BlockingDepthGuard RAII in test** — `testCloseEventPushes99WhenBlocking` uses `{ BlockingDepthGuard g; win->close(); }` instead of inventing a testing-only hook. Cleaner than adding a `pushBlockingDepthForTesting()` accessor that would leak into production API surface.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] Force-link keepalive for xvue_qt_mail_actions.cpp**
- **Found during:** Task 2 — running the new `xvue_qt_mail_menu_tests` for the first time surfaced the classic GNU ld archive-search failure mode: `xvue_qt_mail_actions.cpp.o` was present in `libxvueqt.a` but never linked into any dependent binary (tests or pp*_qt) because the weak `registerMailActions_stub_` in `xvue_qt_api.cpp.o` already "resolved" the dispatch reference.
- **Issue:** Plan 02's strong-override design was silently broken for every linked binary. `pp/ppmail_qt` ran with the warn-once stub — "xvue-qt: registerMailActions stub (Phase 6.1 adds the real body)." — and came up with NO Mesh menu, NO QActions, NO toolbar entries from Plan 02. Plan 02's CI only exercised `xvue_qt_window_chrome_tests` which checks `hasRegisteredModule()` (set by the DISPATCH, not the per-module body) — it never asserted that QActions actually existed. The regression was latent from 2b988be → 8491756.
- **Fix:** Added `extern "C" int xvue_qt_mail_actions_keepalive()` in `xvue_qt_mail_actions.cpp` and a static `g_xvue_qt_mail_actions_keepalive_ref` initialization in `xvue_qt_app.cpp` that calls it. This forces GNU ld to pull the mail_actions TU out of the archive, which in turn displaces the weak stub with the strong body.
- **Files modified:** `xvue/qt/src/xvue_qt_mail_actions.cpp`, `xvue/qt/src/xvue_qt_app.cpp`
- **Verification:** `nm pp/ppmail_qt | grep -c ' T registerMailActions_stub_'` returns 1 (was 0, weak). All 5 D-13 tests pass where before the 4 required cases failed with "Mesh menu not found".
- **Committed in:** `ea7c9df` (Task 2 commit)

**2. [Rule 3 - Blocking] Q_INIT_RESOURCE(xvue_icons) missing**
- **Found during:** Task 2 — `testFileImport` etc. spammed `qt.svg: Cannot open file :/xvue/qt/icons/icons/mail/mesh-point-add.svg` warnings during `initTestCase`.
- **Issue:** Same archive-pull failure mode as #1, but for `qrc_xvue_icons.cpp.o`. Plan 02 registered 10 SVG entries in `xvue_icons.qrc` but never added a `Q_INIT_RESOURCE(xvue_icons)` call. The resource init symbol was unreferenced; the linker skipped the `qrc_xvue_icons.cpp.o` archive member; the icon data was not in the binary. QActions displayed a blank icon and Qt's SVG renderer complained on every access.
- **Fix:** Added `Q_INIT_RESOURCE(xvue_icons)` next to the existing `Q_INIT_RESOURCE(xvue_fonts)` inside `XvueApp::load_bundled_font_()`. Mirrors the 6.0 pattern for fonts.
- **Files modified:** `xvue/qt/src/xvue_qt_app.cpp`
- **Verification:** SVG warnings gone from test output. `nm pp/ppmail_qt | grep qInitResources_xvue_icons` shows `T _Z25qInitResources_xvue_iconsv` now linked in.
- **Committed in:** `ea7c9df` (Task 2 commit — same logical fix as #1)

**3. [Rule 3 - Blocking] XVUE_QT_DISABLE_STDOUT_REDIRECT=1 in test main()**
- **Found during:** Task 2 — first run of the new test exited with no visible Totals line; only QtTest's "Start testing" banner and thread-destruction warnings reached the terminal.
- **Issue:** `xvue_module_init_` calls `installStdoutRedirect()` which `dup2`s STDOUT_FILENO onto a pipe backing the console dock. QtTest's PASS/FAIL/Totals output was silently routed into the dock and never surfaced.
- **Fix:** Set `qputenv("XVUE_QT_DISABLE_STDOUT_REDIRECT", "1")` at the top of `main()` before `XvueApp::ensure()`. Same pattern already proven by `test_xvue_qt_window_chrome.cpp:257`.
- **Files modified:** `xvue/qt/tests/test_xvue_qt_mail_menu.cpp` (test file itself — not a production code change)
- **Verification:** QtTest now prints full Totals line and per-test PASS/FAIL markers under `QT_QPA_PLATFORM=offscreen`.
- **Committed in:** `ea7c9df` (Task 2 commit)
