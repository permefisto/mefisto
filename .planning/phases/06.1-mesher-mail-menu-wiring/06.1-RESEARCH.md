### Pattern 2: Bilingual menu-file parser (D-12)

**What:** Load `td/m/<menu>` at runtime, parse the `( N : 'label' , … )` block into `QMap<int, QString>`, expose `.title()` and `.label(int)`.

**When to use:** At `registerMailActions_stub_` start — once per reachable sub-menu. Result stored in a flyweight `QHash<QString, MenuFile>` keyed by filename.

**Grammar (empirically verified by reading 8 menu files):**

```
variable <TAG> '<title>' entier
( <NUM1> : '<label1>' ,
  <NUM2> : '<label2>' , ...
  <NUMN> : '<labelN>' ) ;
```

- `<TAG>` = uppercase identifier, e.g. `DEBUT`, `MODIFM2D`.
- `<title>` = single-quoted string; may contain spaces, accented chars, `&`, but no single-quote characters in the files observed.
- `<NUMi>` = decimal integer (1-3 digits).
- `<labeli>` = single-quoted; inside the quotes, embedded single-quotes use Fortran-style doubling: `'d''un'` means literal `d'un`.
- Comma-separator may appear at start of continuation line (`, N :`) or end of previous line (`N : 'x',`).
- Closing `) ;` terminates.
- **EDGE CASE:** `td/m/modifm2d` line 17 has a typo: `80;` instead of `80:`. User data; don't auto-fix. Parser should tolerate this by skipping malformed lines (or not trying to parse it if no `:` is found).
- **FR files under `td/m/`** are the ORIGINAL. `td/ma/` holds English translations. `td/mf/` is a FR backup (124 vs 124 files, content identical to `td/m/` modulo the `anglais` flag file). The install script copies `td/ma/` → `td/m/` when English is active ([VERIFIED: `util/langue.f:6-9`]). **This means LIMTCL at runtime ALWAYS reads `td/m/`** — it's the English copy on English installs, French on French installs. [VERIFIED: `util/limtcl.f:54`]

**Implementation sketch (minimum viable parser):**

```cpp
// xvue/qt/src/xvue_qt_menu_file_parser.h — NEW
#pragma once
#include <QString>
#include <QHash>
class MenuFile {
public:
    QString title() const { return title_; }
    QString label(int code) const {
        return labels_.value(code, QStringLiteral("%1;").arg(code));
    }
    bool ok() const { return !labels_.isEmpty(); }
private:
    friend class XvueMenuFileParser;
    QString title_;
    QHash<int, QString> labels_;
};

class XvueMenuFileParser {
public:
    // Loads $MEFISTO/td/m/<name>. Caches across calls. On failure, returns
    // a MenuFile whose label(N) yields "N;" (lexicon-path fallback per D-12).
    static const MenuFile& loadFor(const QString& name);
};

// xvue/qt/src/xvue_qt_menu_file_parser.cpp — NEW
#include "xvue_qt_menu_file_parser.h"
#include <QFile>
#include <QRegularExpression>
#include <QTextStream>
#include <QByteArray>

namespace {
QHash<QString, MenuFile>& cache() {
    static QHash<QString, MenuFile> c;
    return c;
}
}

const MenuFile& XvueMenuFileParser::loadFor(const QString& name) {
    auto& c = cache();
    auto it = c.find(name);
    if (it != c.end()) return *it;

    MenuFile mf;
    const QByteArray mefisto = qgetenv("MEFISTO");
    QFile f(QString::fromLocal8Bit(mefisto) + QStringLiteral("/td/m/") + name);
    if (f.open(QIODevice::ReadOnly | QIODevice::Text)) {
        QTextStream ts(&f);
        QString content = ts.readAll();

        // Extract title between the 2 single-quotes after "variable TAG ".
        static const QRegularExpression titleRx(
            R"(variable\s+\S+\s+'((?:[^']|'')*)'\s+entier)",
            QRegularExpression::CaseInsensitiveOption);
        auto tm = titleRx.match(content);
        if (tm.hasMatch()) {
            mf.title_ = tm.captured(1).replace(QStringLiteral("''"), QStringLiteral("'"));
        }

        // Match all N : 'label' pairs.
        static const QRegularExpression pairRx(
            R"((\d+)\s*:\s*'((?:[^']|'')*)')");
        auto mi = pairRx.globalMatch(content);
        while (mi.hasNext()) {
            auto m = mi.next();
            mf.labels_.insert(m.captured(1).toInt(),
                              m.captured(2).replace(QStringLiteral("''"),
                                                    QStringLiteral("'")));
        }
    }
    return *c.insert(name, mf);
}
```

### Pattern 3: `closeEvent` / `File → Quit` → `99;` dispatch (D-09)

**What:** Replace the current `onFileQuit()` and `closeEvent()` logic (which calls `QCoreApplication::quit()` directly) with `menuBridge_->queueLexicon("99;")`. The 4 chars + CR get drained by the next `xvsouris_` call → Fortran SACLAV assembles `KLG(1:4)="99;"` + CR → DONNMF parses → `NMTCL=99` → `prpr/ppmail.f:267,375-379` path `GOTO 9900 → CALL ITEMDS → CALL ARRET(0)` → Fortran exits the process naturally.

**Why this works:** Phase 6.0 Plan 03 already wired `waitForEvent`'s pre-drain to pop from `XvueMenuBridge::pendingChars_` in `WaitMode::Souris` and return `notypeevent=2, nbc=<ascii>` synchronously before entering the nested `QEventLoop`. `"99;"` is 3 chars + CR = 4 reads. The Fortran-side loop naturally consumes them.

**Concrete code change** (xvue/qt/src/xvue_qt_window.cpp):

```cpp
// BEFORE (current lines 340-354):
void XvueWindow::onFileQuit() {
    auto ret = QMessageBox::question( /* ... */ );
    if (ret == QMessageBox::Ok) {
        close();
        QCoreApplication::quit();
    }

// AFTER (Phase 6.1 — silent dispatch per D-09 "Claude's Discretion default"):
void XvueWindow::onFileQuit() {
    if (menuBridge_) {
        // D-09: push the typed lexicon equivalent. Fortran's save path
        // runs when SACLAV's line buffer contains "99;" + CR and DONNMF
        // dispatches NMTCL=99 → prpr/ppmail.f:9900 → CALL ARRET(0) exits.
        if (auto* dock = consoleDock_) {
            dock->appendLine(QStringLiteral("[menu] 99;"));
        }
        menuBridge_->queueLexicon(QStringLiteral("99;"));
    }
    // Do NOT call close() or QCoreApplication::quit() — Fortran owns the
    // exit.
}

// closeEvent rewrite:
void XvueWindow::closeEvent(QCloseEvent* event) {
    // Persist geometry as before.
    XvuePrefs::saveWindowGeometry(saveGeometry());
    XvuePrefs::saveWindowState(saveState());
    if (consoleDock_) {
        XvuePrefs::saveConsoleVisible(consoleDock_->isVisible());
    }

    // D-09: IF a Fortran blocking read is currently active, intercept the
    // close — push 99; and IGNORE the close. Fortran will drain the queue
    // and call ARRET() itself.
    if (menuBridge_ && XvueApp::blockingDepth() > 0) {
        menuBridge_->queueLexicon(QStringLiteral("99;"));
        event->ignore();   // don't actually destroy the window yet
        return;
    }
    // No blocking read active — window is closing for another reason
    // (QCoreApplication::quit from atexit, child of QApplication teardown).
    // Fall through to default close.
    QMainWindow::closeEvent(event);
}
```

**Pitfall:** `closeEvent` runs on the main thread synchronously. If we `queueLexicon("99;")` and then `event->ignore()`, Qt's event loop continues. The NEXT `xvsouris_` from Fortran's main loop pops the queued char, returns to SACLAV, which assembles `99;` + CR, line completes, DONNMF dispatches, Fortran exits via `CALL ARRET(0)` → `STOP` → process terminates naturally. The "Save data and quit" path does its work. The QApplication gets destroyed in `atexit` — same behaviour as today when the user types `99;` at the prompt.

### Pattern 4: `[menu]` echo to console dock (D-07)

**What:** Before `queueLexicon(cmd)`, append `[menu] cmd` to the console dock so the user sees the typed equivalent scroll past.

**Example** (embedded in `makeLeafAction` lambda above):

```cpp
if (auto* dock = win->consoleDock()) {
    dock->appendLine(QStringLiteral("[menu] ") + lexicon);
}
mb->queueLexicon(lexicon);
```

The bilingual neutrality is explicit: the `[menu]` prefix stays the same in FR/EN (D-07 notes this is acceptable). No new `MsgId` entries needed.

### Anti-Patterns to Avoid

- **Anti-pattern: `QMessageBox::question` on Quit.** Phase 6.0 has it today (with FR/EN confirm); 6.1 D-09 default is **silent** dispatch. Remove the confirm dialog from `onFileQuit` to match typed-lexicon behaviour.
- **Anti-pattern: building QActions in `XvueWindow` ctor.** Mail-specific actions MUST be in `registerMailActions_stub_` override — the ctor runs for the shared shell before `xvue_module_init_` is called from Fortran. Adding mail-specific actions in the ctor would break the per-module abstraction.
- **Anti-pattern: registering a bare-char shortcut.** `QAction::setShortcut(QKeySequence("5"))` steals `5` from the typed lexicon. `verify_shortcut_modifiers.sh` catches this at build time.
- **Anti-pattern: calling Fortran `DFPOIN` / `DFLIGN` etc. directly from C++.** Phase 6.1 never does this — QActions only queue lexicon chars. Fortran dispatches itself.
- **Anti-pattern: mutating `XvueWindow` existing QActions (File→Open, etc.) to push mail lexicon.** The shared 6.0 actions stay generic — they push NOTHING from the 6.1 side. Only NEW mail-specific QActions queue lexicon. The `onRecentProjectRequested` handler at `xvue_qt_window.cpp:391-397` is commented "6.1+ queues the module-specific open lexicon here" — Phase 6.1 decides whether to implement that or leave it for a polish phase.

## Common Pitfalls

### Pitfall 1: X11 build breaks before Qt strong override lands

**What goes wrong:** A plan lands `CALL XVUE_MODULE_INIT('mail')` in `prpr/ppmail.f` WITHOUT landing the `xvue/xvmodi.f` no-op stub first. Then `bin/cbl_tout` fails to link `pp/ppmail` (unresolved `xvue_module_init_`).

**Why it happens:** Two different build paths share `prpr/ppmail.f`. The Qt path resolves `xvue_module_init_` via `libxvueqt.a` (already has the strong symbol in `xvue_qt_api.cpp:1452`). The X11 path links `xvue/xvuelc.o + xvue/lib`, neither of which defines `xvue_module_init_`.

**How to avoid:**
1. Plan 03 MUST land `xvue/xvmodi.f` in the SAME commit as the `prpr/ppmail.f` edit.
2. CI sanity (manual, no CI): run `bin/cbl_tout` once AFTER the commit, verify `pp/ppmail` built and `$MEFISTO/pp/ppmail --help` doesn't crash.
3. Alternatively: land `xvue/xvmodi.f` in an EARLIER commit within the same plan, run `bin/cbl_tout`, then land the Fortran edit.

**Warning signs:** `gfortran ... prpr/ppmail.f ... mail/lib util/lib xvue/lib xvue/xvuelc.o -lgfortran -lX11 -o pp/ppmail` errors with `undefined reference to 'xvue_module_init_'`.

**Recommended xvmodi.f content:**


### Pitfall 2: Parallel `cbl_tout` + `cbl_tout_qt` corrupt `pp/`

**What goes wrong:** Plan 03 verification accidentally runs both build scripts in background shells to save time. Concurrent linkers write to `pp/ppmail*` and clobber each other mid-link. One (or both) binary ends up in a broken state; next run of tests shows false positives.

**Why it happens:** Both scripts share `$MEFISTO/pp/` as the output dir. Documented in `~/.claude/projects/-home-drico-git-mefisto/memory/feedback_parallel_builds_share_pp.md`.

**How to avoid:** Plans MUST serialize: `bin/cbl_tout_qt && bin/cbl_tout` (note the `&&`). Never `&`. Never two shells. Never a Makefile with both as targets.

**Warning signs:** Rebuild says "SUCCESS" but `pp/ppmail_qt` segfaults, or `nm libxvueqt.a | grep _$ | wc -l` returns a wrong count, or pp/ppmailN says "INCORRECT" out of nowhere.

### Pitfall 3: `99;` close-dispatch with no Fortran blocking read active

**What goes wrong:** User closes the window while Fortran is NOT in a blocking read (e.g. sitting idle after a long compute has ended but before `xvsouris_` is called again). `queueLexicon("99;")` enqueues chars, `event->ignore()` keeps the window open — but no `xvsouris_` call ever drains the queue. User is stuck with a window that refuses to close.

**Why it happens:** The pre-drain only fires inside `waitForEvent(WaitMode::Souris)`. If Fortran is between calls, the queue holds chars indefinitely.

**How to avoid:** The `closeEvent` handler checks `XvueApp::blockingDepth() > 0` before ignoring. If depth is 0, Fortran is either batch (no interactive loop) or dead — fall through to default close and let Qt tear down the window. Code in Pattern 3 above already does this.

**Edge case:** MEFISTO's main loop always returns to `LIMTCL('debut', …)` between commands — i.e., it's ALMOST always in a blocking read. But during `CALL DFPOIN` (`Mesh → Points → Create`) the user might be several `CALL LIMTCL`s deep in nested menus. `blockingDepth()` is 1 or more during all of these — so `event->ignore()` is correct.

**Warning signs:** QTest case `testWindowCloseDispatchesSaveQuit` sees `event->ignore()` called but the next `xvsouris_` returns wrong data.

### Pitfall 4: Offscreen QTest flakes (deferred-items.md #1/#2 replay)

**What goes wrong:** `xvue_qt_mail_menu_tests` uses `QCoreApplication::postEvent + processEvents(ExcludeUserInputEvents)` to simulate a menu click → `waitForEvent` never sees the trigger → assertion times out. Same failure mode as 06.0 deferred-items.md #1.

**Why it happens:** `processEvents(ExcludeUserInputEvents)` drops QActionEvent etc. under offscreen QPA.

**How to avoid:** **Simulate QAction triggers by calling `QAction::trigger()` directly, not by posting mouse/key events.** `QAction::trigger()` runs synchronously on the main thread; the connected lambda calls `queueLexicon("1;1;")` immediately. Then call `xvsouris_(&n, &c, &x, &y)` 4 times — each reads one char from the queue via the existing pre-drain path. [VERIFIED: `xvue/qt/tests/test_xvue_qt_window_chrome.cpp:199` uses `openAct->trigger()` pattern]

**Warning signs:** Test hangs on first iteration; `queueSize()` unchanged after "trigger."

### Pitfall 5: `td/m/modifm2d` typo (`80;` instead of `80:`)

**What goes wrong:** Parser's `(\d+)\s*:\s*'(...)` regex doesn't match the `80;` line; parser returns `label(80)` = `"80;"` (fallback). QAction for `Modify 2d mesh → Save` shows `80;` instead of "SAVE the MESH on FILE xyznsef.s.NomSurface".

**Why it happens:** Real typo in user-authored data file.

**How to avoid:** Two choices:
1. **Tolerant parse:** accept `;` as alternative to `:` in the pair regex. Silent behaviour. Risk: hides other typos.
2. **Log-and-fallback:** regex matches only `:`; on parse failure the fallback `"N;"` shows and stderr logs once. Explicit.

**Recommendation:** (2) log-and-fallback. The audit markdown records the typo; a future polish pass can fix the data file.

**Warning signs:** QAction labelled `"80;"` (not the French string) when running in FR mode with `td/m/modifm2d` containing the typo.

### Pitfall 6: `XvueConsoleDock::appendLine` during stdout-redirect loop

**What goes wrong:** The `[menu] 1;1;` echo (D-07) writes to the console dock via `dock->appendLine(...)`. But `installStdoutRedirect` (Plan 04) has already redirected `stdout` to a pipe that feeds the dock. If `appendLine` internally `printf`s, we get a recursive loop.

**Why it happens:** Plan 04 captures `stdout` file descriptor; echo via `printf` would go through the pipe back to the dock.

**How to avoid:** `XvueConsoleDock::appendLine(QString)` is documented to DIRECTLY call `QPlainTextEdit::appendPlainText` — NOT go through stdout. [VERIFIED: xvue/qt/src/xvue_qt_console_dock.cpp — grep for "appendLine" shows a direct widget call]. So direct-dock writes are safe.

**Warning signs:** Console dock shows `[menu] [menu] [menu] ...` in escalating recursion.

### Pitfall 7: `QMenu` parent `QMenuBar` already contains a `File` menu

**What goes wrong:** Plan 02 tries to `mbar->addMenu(tr("&File"))` but 6.0's `XvueWindow::buildMenuBar` has already added a File menu (object name `"File"`). Two File menus appear side-by-side.

**Why it happens:** 6.0 builds `{File, View, Help}` in the ctor. 6.1 must APPEND to these, not recreate them.

**How to avoid:** Use `mbar->findChild<QMenu*>("File")` — existing from 6.0. Add new actions via `findChild<QMenu*>("File")->addAction(...)`. For the NEW `Mesh` menu only, `mbar->addMenu(...)` is correct. [VERIFIED: 6.0 already calls `fileMenu->setObjectName("File")` at xvue_qt_window.cpp:129]

**Warning signs:** Menu bar shows `File File View Help` or `File Mesh View Help File` (duplicate File).

### Pitfall 8: `registerMailActions` linked to BOTH elas/flui/ther/nlse binaries

**What goes wrong:** `xvue_qt_mail_actions.cpp` is added to `xvue/qt/CMakeLists.txt target_sources(xvueqt ...)`. `libxvueqt.a` now contains `registerMailActions_stub_` as a strong symbol for EVERY pp*_qt binary. Solver binaries (ppelas_qt etc.) pull it in even though they CALL `xvue_module_init_('elas')` and expect the elas stub. Because the mail strong symbol dispaces the elas weak symbol, ALL modules' action registration funnels through `registerMailActions` regardless of actual module name.

**Wait — no.** Re-reading `xvue_qt_api.cpp:1486-1490`: the dispatch uses `if (mod == "mail") registerMailActions_stub_(...)`. So the weak/strong override only affects what happens when `"mail"` is the module. Elas/flui/ther/nlse calls dispatch to their own `_stub_` symbols, which stay weak until 6.2-6.5 land.

**Verdict:** No actual bug — the dispatch is module-specific. The strong mail symbol only fires when `mod == "mail"`. **Keep the `target_sources` addition in `libxvueqt.a` — it's fine.**

**Alternative considered (and rejected):** linking `xvue_qt_mail_actions.o` ONLY into `pp/ppmail_qt` via a per-module `add_executable` CMake rule. Adds complexity; all solvers would need per-module CMake machinery. **Overkill.** The weak/strong dispatch in `xvue_qt_api.cpp` is the correct abstraction.

## Open Questions

1. **`xvue_module_init_` call order: before vs after `XVINIT`?**
   - What we know: The comment at `xvue_qt_api.cpp:1432` says "BEFORE xvinitgraphique_" but the dispatch body Step 3 calls `win->consoleDock()->installStdoutRedirect()` which requires `XvueWindow` to exist. `XvueWindow` is constructed inside `xvinitgraphique_` (via `XvueApp::window_slot()`).
   - What's unclear: Which path is right — is the comment wrong, or is there a subtle path where `win` is non-null before `xvinitgraphique_`?
   - Recommendation: Read `xvue_qt_api.cpp::xvinitgraphique_` implementation and the `xvue_module_init_` body lines 1477-1480 together during Plan 03. Update the stale comment in Plan 03.

2. **`LEXICON-AUDIT-mail.md` row count (D-11 estimate vs actual)?**
   - What we know: D-11 estimates 100-150 rows. Example 5 (this research) finds 42 sub-menus + `debut` with ~230 total leaves reachable.
   - What's unclear: Should the audit include util-shared sub-menus (e.g., `couleurs`, `non_oui`) in full, or only once with a "shared" column? A full expansion would yield ~230 rows; a de-duplicated tree would be closer to 100-150.

3. **X11 no-op stub location (`xvue/xvmodi.f` vs `util/xvmodi.f` vs in `xvuelc.c`)?**
   - What we know: `xvue/*.f` files get archived into `xvue/lib` by `bin/cbl_tous_f xvue` (`bin/cbl_tout:60`). `util/*.f` → `util/lib`. `ppmail` links both. Either location works.
   - What's unclear: Which is the "right" home?
   - Recommendation: **`xvue/xvmodi.f`** — the symbol is a hook for the xvue graphics layer (Qt-side body lives there). Keep X11 and Qt "logical homes" aligned by module.

4. **Is the bilingual parser cached across `registerMailActions` invocations?**
   - What we know: `xvue_module_init_` is called once per process (6.0 contract). So the parser is called once per sub-menu per process. A static cache at file scope is fine.
   - What's unclear: What about tests that call `xvue_module_init_` multiple times?
   - Recommendation: Static `QHash<QString, MenuFile>` cache at file scope. Entries never evicted; cache grows to at most 42 entries (all sub-menus). Test-mode cache-clear via a `#ifdef XVUE_QT_TESTING` helper.

5. **Does the `[menu]` echo break 6.0 Plan 04's stdout-redirect tests?**
