## Decisions Made

- **Widened validator row-count bound from `[100, 150]` (CONTEXT D-11) to `[80, 250]` (RESEARCH Validation Architecture rule 2).** Rationale: RESEARCH Example 5 empirically counted ~230 reachable leaves; even with 19 shared-util compressions, actual row count landed at 211. The widened bound preserves D-11's intent (bounded audit, not unbounded) while admitting the empirical reality.

- **Compressed-row lexicon_path format uses a representative parent-entry numeric path (e.g. `70;1;1;` for suivitms reached from managmef entry 1)**, NOT a synthetic marker (e.g. `util;*;` or `70;1;*;`). Rationale: the strict `LEX_RX = \d+;(?:\d+;)*` regex in the validator rejects non-numeric paths; rather than loosening the regex (which would silently admit malformed audits), each compressed row points to a valid parent-entry path and documents the full leaf count in the `notes` cell.

- **Top-5 toolbar set kept verbatim from RESEARCH A8** — no user-driven swaps during auto-mode review. Rationale: the 5 chosen leaves (Type-point, Lines, Surfaces, Draw-mesh, Save-Quit) cover the 5 highest-frequency leaves in `testa/*/*.mesh` (counts 65, 26, 34, 22, and Save-Quit by convention since every session ends with it). User can request swaps as a follow-up edit after the phase completes.

- **Rule 9 (SVG file existence) is WARN-only in Plan 01.** Rationale: Plan 01 produces the audit listing 8 required SVG filenames; Plan 02 creates the actual `.svg` files under `xvue/qt/resources/icons/mail/`. During Plan 01 execution the files don't exist yet, so a FAIL would block the validator. Plan 02 acceptance flips the gate via `AUDIT_STRICT_ICONS=1`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Plan's Task 1 acceptance regex #5 doesn't actually count `high` rows**

- **Found during:** Task 1 acceptance verification
- **Issue:** The plan's acceptance criterion 5 uses `grep -cE '^\|[^|]*\| *high *\|'`. This regex matches a row whose COLUMN 2 ends with `high` — but in our schema, `frequency=high` is in COLUMN 4. The regex returns 0 even when the audit correctly contains 14 high-frequency rows.
- **Fix:** Ignored the literal regex and used the validator's semantic Rule 4 check instead (Python iterates each row and checks `r[3] in FREQ_OK`). Documented the plan's regex as a spec bug. 14 rows have `frequency=high`, exceeding the "at least 8" target.
- **Files modified:** none (the plan's regex is a doc artifact, not a checked-in script)
- **Verification:** `python3 -c '... Counter(r[3] for r in data) ...'` returned `{'high': 14, 'med': 17, 'low': 180}`
- **Committed in:** 183e39e (Task 1)

**2. [Rule 3 - Blocking] First draft of compressed-row lexicon_path used `*` markers, violating Rule 3 regex**

- **Found during:** Task 1 initial draft (before commit 183e39e)

- **Fix:** Converted all compressed-row paths to a valid representative parent-entry numeric path (e.g. `10;36;1;` for couleurs reached from tracmail 36, `70;1;1;` for suivitms reached from managmef 1). The `notes` cell retains the compression marker and documents the actual leaf count.
