# Phase 06.2 Gap-Closure: Code Review Report

**Reviewed:** 2026-04-27
**Depth:** standard
**Files Reviewed:** 7
**Status:** issues_found

## Summary

This review covers the Plan 04 (`ensureTopLevelMenu` insertion-order fix) and Plan 05
(bilingual `td/ma/` path in `XvueMenuFileParser`) gap-closure changes.

The core logic in both plans is sound. No critical security or correctness bugs were
found. Three warnings and two info items are documented below. The most significant
issue is that `clearCacheForTesting()` ships in the production binary without any
compile-time guard, contrary to the comment in the header that says it is "guarded by
`XVUE_QT_TESTING`". The remaining findings concern a cache-coherence hazard between
the `xvueIsEnglish()` static and the parser cache, and a silent fallback path in
`ensureTopLevelMenu` that can produce incorrect menu ordering without any warning.

## Warnings

### WR-01: `clearCacheForTesting()` is not compile-gated — ships in production binary

**File:** `xvue/qt/src/xvue_qt_menu_file_parser.h:55-56`, `xvue/qt/src/xvue_qt_menu_file_parser.cpp:107-109`

**Issue:** The header comment says the method is "Guarded by `XVUE_QT_TESTING`; not
called from production paths." However, neither the declaration nor the definition is
wrapped in `#ifdef XVUE_QT_TESTING`. The function is a publicly-exported member of
`XvueMenuFileParser`, compiled unconditionally into `libxvueqt.a`. Any code path that
reaches `xvue_qt_menu_file_parser.cpp` — including the production `pp/ppelas_qt` and
`pp/ppmail_qt` binaries — exposes `clearCacheForTesting()` as a callable symbol.
Although no production caller currently invokes it, the function's existence in the
shipping binary violates the stated contract and could confuse a future maintainer
into thinking the guard is already in place.

**Fix:** Either wrap both the declaration and the definition in `#ifdef XVUE_QT_TESTING
... #endif`, or remove the misleading comment from the header. The test-only `#define`
should be added in `tests/CMakeLists.txt` via `target_compile_definitions`:

```cmake
# In xvue/qt/tests/CMakeLists.txt, for every test target that includes
# xvue_qt_menu_file_parser.h:
target_compile_definitions(xvue_qt_elas_menu_tests PRIVATE XVUE_QT_TESTING)
target_compile_definitions(xvue_qt_mail_menu_tests PRIVATE XVUE_QT_TESTING)
```

And in the source files:

```cpp
// xvue/qt/src/xvue_qt_menu_file_parser.h
#ifdef XVUE_QT_TESTING
    static void clearCacheForTesting();
#endif

// xvue/qt/src/xvue_qt_menu_file_parser.cpp
#ifdef XVUE_QT_TESTING
void XvueMenuFileParser::clearCacheForTesting() {
    cache().clear();
}
#endif
```

### WR-02: Parser cache and `xvueIsEnglish()` static are incoherent in tests — `clearCacheForTesting()` does not reset the language probe

**File:** `xvue/qt/src/xvue_qt_menu_file_parser.cpp:60`, `xvue/qt/src/xvue_qt_i18n.cpp:107-115`, `xvue/qt/tests/test_xvue_qt_elas_menu.cpp:277-300`

**Issue:** `XvueMenuFileParser::clearCacheForTesting()` clears `cache()` (the
`QHash<QString, MenuFile>` static), but the language probe `xvueIsEnglish()` is
separately cached as a `static const bool` initialized at first call
(`xvue_qt_i18n.cpp:107`). In `testBilingualLabelsEnglish`, the test verifies that the
anglais flag is on disk before calling `clearCacheForTesting()` and then calling
`loadFor("debuelas")`. If a _previous_ test in the same process called
`xvueIsEnglish()` when the environment had no anglais flag (for example, in a CI
environment where `MEFISTO` is set but `td/m/anglais` does not exist), `xvueIsEnglish()`
would have already cached `false`. Clearing the `MenuFile` cache has no effect on this
boolean — the subsequent `loadFor()` will call `xvueIsEnglish()` again, receive the
cached `false`, and silently load `td/m/debuelas` instead of `td/ma/debuelas`,
causing the `QCOMPARE` assertions on English strings to fail non-deterministically
depending on test execution order.

The `initTestCase` slot runs `xvinitgraphique_()` and `xvue_module_init_()`, both of
which may trigger `xvueIsEnglish()` before `testBilingualLabelsEnglish` has a chance
to verify the flag's presence on disk. If the anglais flag is absent at that point,
the boolean is permanently locked to `false` for the process lifetime.

**Fix:** Add a `clearLanguageCacheForTesting()` companion (also `XVUE_QT_TESTING`-gated)
to `xvue_qt_i18n` that resets the boolean, and call it alongside
`clearCacheForTesting()` in `testBilingualLabelsEnglish`. Alternatively, document
explicitly in the test's `QSKIP` block that the test must be the _first_ process to
call `xvueIsEnglish()` and restructure test ordering accordingly.

```cpp
// xvue/qt/src/xvue_qt_i18n.h (under #ifdef XVUE_QT_TESTING)
void xvueClearLanguageCacheForTesting();

// xvue/qt/src/xvue_qt_i18n.cpp (under #ifdef XVUE_QT_TESTING)
// NOT possible with a static const bool — requires refactor to a
// static bool + a reset flag, or a function-level std::optional.
```

The minimum-footprint fix without a refactor is to re-order `testBilingualLabelsEnglish`
to be the first slot (before `initTestCase` calls any function that touches
`xvueIsEnglish()`), add a comment explaining the ordering constraint, and treat the
static-local caching of `xvueIsEnglish()` as a known limitation in the test harness.
That at least prevents silent CI failures; the proper fix requires making the language
probe resettable.

### WR-03: Silent no-op in `ensureTopLevelMenu` when `insertBefore` anchor is not found — menu appended instead of inserted

**File:** `xvue/qt/src/xvue_qt_elas_actions.cpp:213-217`, `xvue/qt/src/xvue_qt_mail_actions.cpp:217-223`

**Issue:** Both `registerElasActions_stub_` and `registerMailActions_stub_` look up the
View menu via `mbar->findChild<QMenu*>("View")` and pass the result as the
`insertBefore` anchor. If the View menu has not yet been created at call time (e.g. the
shared 6.0 chrome was not wired, or a future refactor reorders initialization),
`viewMenuForAnchor` will be `nullptr`. `ensureTopLevelMenu` then falls through to the
`addMenu(m)` branch, silently appending Solve/Mesh after Help instead of before View.
The resulting menu order `{File, Help, Solve}` or `{File, Help, Mesh}` would violate
the conformance contract and the new `testMenuOrder` test would catch it — but only at
test time, not at the point of the logic error.

There is no assertion or `qWarning()` on the `viewMenuForAnchor == nullptr` case. A
future change that moves chrome initialization later in the startup sequence would
silently break the ordering without a clear diagnostic.

**Fix:** Add a `Q_ASSERT` or `qWarning()` when the expected anchor is absent, so the
failure is loud in debug builds and visible in logs:

```cpp
// In registerElasActions_stub_ (elas_actions.cpp:213) and
// registerMailActions_stub_ (mail_actions.cpp:217):
auto* viewMenuForAnchor = mbar->findChild<QMenu*>(QStringLiteral("View"));
Q_ASSERT_X(viewMenuForAnchor != nullptr,
           "registerElasActions_stub_",
           "View menu not found — Solve will be appended after Help "
           "(expected {File, Solve, View, Help} order)");
auto* solveMenu = ensureTopLevelMenu(mbar,
    QObject::tr("&Solve"),
    QStringLiteral("Solve"),
    viewMenuForAnchor);
```

This does not change runtime behaviour in the happy path but makes the failure visible
in debug builds and in test output instead of silently producing a wrong menu order.

### IN-01: `addToolbarByLexicon` searches only two levels — silently skips three-level-deep actions

**File:** `xvue/qt/src/xvue_qt_elas_actions.cpp:110-127`, `xvue/qt/src/xvue_qt_mail_actions.cpp:119-136`

**Issue:** `addToolbarByLexicon` walks the top-level actions of `menu` and descends
one level into sub-menus (`a->menu()->actions()`), but no deeper. The elas View menu
contains actions nested at two submenu levels (e.g. `8;1;1;` lives under
`View > DrawStress > Stresses`). The toolbar currently only asks for `"8;"` (which is
the "Draw displacements & stresses..." parent leaf added directly to `drawStressMenu`
at line 309), so the current depth of two is sufficient for all five lexicons requested
by both modules. However, the function's comment says "one level of its submenus"
without noting this depth limit, and future callers adding a three-level-deep toolbar
entry would silently fail to find it.

**Fix:** Either document the two-level limit explicitly in the comment and in any
future callers, or make the helper recursive (matching the depth-unlimited
`actionByLexicon` already used in the test files):

```cpp
// Option A: document the limit
// Scan `menu` (top level + one submenu level) for a QAction whose
// `lexicon` dynamic property matches `lex`.
// NOTE: does NOT recurse beyond one submenu level. If a target action
// lives more than one level deep, use a recursive helper instead.

// Option B: make it recursive (matches actionByLexicon in tests)
void addToolbarByLexicon(QToolBar* tb, QMenu* menu, const QString& lex) {
    if (!tb || !menu) return;
    for (QAction* a : menu->actions()) {
        if (a->property("lexicon").toString() == lex) {
            tb->addAction(a); return;
        }
        if (a->menu()) addToolbarByLexicon(tb, a->menu(), lex);
    }
}
```

### IN-02: `static bool registered` in `registerElasActions_stub_` ties guard to process lifetime — unsafe if multiple XvueWindows are ever created

**File:** `xvue/qt/src/xvue_qt_elas_actions.cpp:158-160`

**Issue:** The one-shot guard uses a function-level `static bool registered = false`.
This means the guard is tied to the process lifetime, not to the `XvueWindow` instance.
The comment correctly notes that "registerElasActions_stub_ must only be called once
per XvueWindow lifetime" and that "xvue_module_init_ is the sole intended call site."
However, if a second `XvueWindow` were ever created in the same process (e.g. in a
future test that calls `xvfermer_()` followed by a second `xvinitgraphique_()`), the
second window would receive no elas actions at all because `registered` is already
`true`. The mail module (`registerMailActions_stub_`) does not have this guard at all,
relying entirely on `ensureTopLevelMenu`'s idempotency — which is inconsistent.

This is an info item because the current process model is single-window-per-process,
but the asymmetry between elas and mail and the cross-instance scope of the guard are
worth noting for Phase 6.3+ work.

**Fix:** Document the single-window-per-process assumption in a comment alongside the
guard, and confirm whether the mail module intentionally omits the guard (relying on
idempotency of `ensureTopLevelMenu`) or whether it should also have one. A consistent
policy prevents silent double-registration bugs in future phases:

```cpp
// If single-window-per-process is a hard invariant (enforced by XvueApp):
// static bool registered = false;  // safe: process owns exactly one window
// If future phases allow window recycling, replace with a per-window flag
// stored on XvueWindow (e.g. win->setProperty("elasRegistered", true)).
```
