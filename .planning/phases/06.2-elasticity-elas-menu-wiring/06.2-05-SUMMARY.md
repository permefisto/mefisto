## Decisions Made

- **Fix location: shared parser, not per-module:** The gap-closure scope explicitly requires generalization via the audit parser ("fix must generalize via the audit parser, not hard-code per module"). The parser fix benefits 6.1 mail today and 6.3/6.4/6.5 in the upcoming waves at zero per-module cost. Per-module workarounds would have multiplied the failure surface and made the bilingual contract harder to lock with one regression test.
- **QFile::exists() pre-check, not errno-based fallback:** The td/ma/ path is gated by `QFile::exists()` BEFORE QFile::open is called. If the file is missing (or unreadable for any reason), `chosen_path` stays empty and we fall through to td/m/. This keeps the fall-through deterministic and avoids any ambiguity from QFile's open-error reporting (which on Linux conflates ENOENT, EACCES, EISDIR, etc.).
- **xvueIsEnglish() static-cache caveat preserved:** The probe is set ONCE at first call (per its existing comment in xvue_qt_i18n.cpp: "users toggle the language by creating or removing $MEFISTO/td/m/anglais then restarting the process; live toggling mid-process is not supported (mirrors Fortran-side LANGUE)"). The new test relies on testBilingualLabelsEnglish being the FIRST consumer of xvueIsEnglish() in the binary — verified by reading the other slots, none of which call xvueT() or xvueIsEnglish() before testBilingualLabelsEnglish runs (registerElasActions_stub_ uses raw QStringLiteral and parser titles, not xvueT()).
- **Test placement: elas only this plan; mail deferred:** Adding a parallel mail testBilingualLabelsEnglish slot is mechanical copy-paste (substitute `debuelas` → `debut` and pick canonical EN strings from `td/ma/debut`), but it isn't gating any further wave — and the 6.0 / 6.1 / 6.2 chain would have lost momentum on a duplicate test. The parser fix itself benefits mail in production today; only the regression-guard slot is one-sided.
- **Helper duplication discipline still preserved:** No changes to xvue_qt_elas_actions.cpp or xvue_qt_mail_actions.cpp this plan — the parser fix is upstream of those TUs. ensureTopLevelMenu and the per-module register stubs stay verbatim from Plan 04.

## Hand-off note for 6.3 / 6.4 / 6.5

When 6.3 (Fluid), 6.4 (Thermal), 6.5 (Nonlinear) wire their per-module register stubs and ship menu test binaries, the bilingual treatment is **automatic** — they don't need to touch the parser. Two recommendations:

1. **No per-module parser changes:** XvueMenuFileParser already reads `td/ma/<name>` for any `<name>` you pass in (debuflui / debuther / debunlse), so the EN labels flow through automatically as long as `$MEFISTO/td/ma/<name>` exists. If a module's td/ma/ file is missing, the fall-through to td/m/<name> kicks in transparently.

2. **Add a per-module testBilingualLabelsEnglish slot:** Mirror the elas pattern (xvue/qt/tests/test_xvue_qt_elas_menu.cpp lines 245-300, slot `testBilingualLabelsEnglish`). The skeleton is:
   - QSKIP if MEFISTO env / `td/m/anglais` / `td/ma/<your-debu-file>` is missing
   - Call `XvueMenuFileParser::clearCacheForTesting()` before and after the body
   - Call `XvueMenuFileParser::loadFor("<your-debu-file>")` (e.g., "debuflui")
   - QCOMPARE 2-4 canonical EN strings from `td/ma/<your-debu-file>`

3. **xvueIsEnglish() first-consumer caveat:** Each test binary should ensure testBilingualLabelsEnglish runs BEFORE any slot that consumes xvueT() (which would seed the static-local cache before the slot can verify). In the elas binary none of the other slots call xvueT() so the slot's natural alphabetical ordering inside `private slots:` is fine. For 6.3/6.4/6.5 binaries, audit the slot bodies the same way — if a future slot calls xvueT()/tr(), reorder so testBilingualLabelsEnglish runs first.
