## Warnings

### WR-01: registerElasActions_stub_ is not idempotent, but the comment claims it is

**File:** `xvue/qt/src/xvue_qt_elas_actions.cpp:180-181`

**Issue:** The comment on `ensureTopLevelMenu` says "Idempotent — repeated registration is safe." This is correct only for the Solve-menu creation block (which uses `findChild` before creating). The File-menu extension (lines 162-176), View-menu extension (lines 264-335), and toolbar-separator + `addToolbarByLexicon` section (lines 344-350) contain no such guard. A second call to `registerElasActions_stub_` would add duplicate separators, duplicate QActions in File and View, and duplicate toolbar buttons. The comment at line 181 gives a false assurance of function-level idempotency.

In production, `ppelas.f` calls `XVUE_MODULE_INIT` exactly once, so this does not manifest as a runtime bug today. However, the misleading comment creates risk for future modules (6.3 flui, 6.4 ther, 6.5 nlse) that will copy this file as their template.

**Fix:** Either add a static registration guard inside `registerElasActions_stub_` (as `xvue_qt_api.cpp` already does for the warn-once stubs), or narrow the comment to only describe the `ensureTopLevelMenu` helper:

```cpp
// ensureTopLevelMenu is idempotent -- repeated calls for the SAME
// objectName return the existing QMenu. The outer
// registerElasActions_stub_ function itself should only be called once
// per XvueWindow lifetime; xvue_module_init_ is the sole call site.
QMenu* ensureTopLevelMenu(QMenuBar* mbar,
                          const QString& title,
                          const QString& objectName)
```

Alternatively, add a one-shot guard to the function body:

```cpp
extern "C" void registerElasActions_stub_(XvueWindow* win,
                                          XvueMenuBridge* mb)
{
    if (!win || !mb) return;
    static bool registered = false;
    if (registered) return;
    registered = true;
    // ... rest of function
}
```

### WR-02: validate_audit_md.py docstring describes "--" but implementation accepts "—" (em-dash)

**File:** `tools/validate_audit_md.py:4` and `tools/validate_audit_md.py:37`

**Issue:** The module docstring (line 4) documents Rule 4 as: `frequency column values in {high, med, low, "--"}`. The implementation (line 37) uses `FREQ_OK = {"high", "med", "low", "—"}` — a Unicode em-dash (U+2014), not ASCII double-hyphen `"--"`. These are different characters. If any audit-file author writes `--` in a frequency cell (trusting the docstring), Rule 4 will fail with an opaque error. The actual elas and mail audit files use only `{high, med, low}` in the frequency column, so there is no current breakage — but the docstring forms a false contract.

**Fix:** Align docstring and implementation. Since no audit file uses either value in the frequency column, the safest fix removes the unnecessary fourth element and updates the docstring:

```python
FREQ_OK = {"high", "med", "low"}
```

And update the docstring line:
```python
    4. frequency column values in {high, med, low}.
```

If the intent is to allow a "not applicable" marker in the frequency column for future audit files, pick one convention and document it consistently:

```python
FREQ_OK = {"high", "med", "low", "—"}  # em-dash U+2014, not "--"
```

And in the docstring: `frequency column values in {high, med, low, "—" (em-dash U+2014)}`.

### IN-01: File-level comment lists "schedyna" as an expanded submenu but it is never loaded

**File:** `xvue/qt/src/xvue_qt_elas_actions.cpp:14`

**Issue:** The composition contract comment at the top of the file lists `schedyna` as one of the menu-files "expanding" within the Solve submenus: `"expanding cl_elas / resoelst / resoelin / schedyna / methreso / therelas / methvvpr"`. However, `schedyna` is never passed to `XvueMenuFileParser::loadFor()` anywhere in the file body, and no submenu or leaf action references it. The `schedyna` menu file is used by `ELAD2T` (called from within the Unsteady solver subroutine) as a sub-prompt, not as a top-level dispatched action accessible from the Qt menu bar. The comment is misleading to future readers maintaining this file.

**Fix:** Remove `schedyna` from the comment listing to match what the code actually loads:

```cpp
//   Solve menu : flat leaves 1;..8; at top level plus Parameters submenu
//                (20;, 38;, 39;) and Input/Static/Unsteady/Eigen submenus
//                expanding cl_elas / resoelst / resoelin /
//                methreso / therelas / methvvpr leaves
```

### IN-02: Rule 9 comment in validate_audit_md.py still references "mail/" as the icon directory

**File:** `tools/validate_audit_md.py:148-149` and `tools/validate_audit_md.py:18`

**Issue:** The module-level docstring (line 18) says rule 9 checks `"xvue/qt/resources/icons/mail/ (Plan 02 deliverable)"`. The inline comment at line 148-149 repeats this. The `resolve_icon_path` function is already module-agnostic — it derives the owning module from the audit filename stem (e.g., `LEXICON-AUDIT-elas` → `elas`) and correctly resolves to `icons/elas/`. The hard-coded `mail/` references in the comments are stale leftovers from the 6.1 copy. They do not affect runtime behavior but will confuse reviewers of elas/flui/ther/nlse audit files.

**Fix:** Update both comment sites to describe the generalized behavior:

```python
       icon_source cells ending in .svg have a matching file under
       xvue/qt/resources/icons/<module>/ (derived from audit filename stem).
       Cross-phase reuse (e.g. 6.2 reusing mail/mesh-draw.svg) is handled
       by the fallback scan of all module subdirectories.
```

### IN-04: test_xvue_qt_elas_menu.cpp discards real argc/argv silently

**File:** `xvue/qt/tests/test_xvue_qt_elas_menu.cpp:264-265`

**Issue:** `main(int argc, char* argv[])` immediately casts both arguments to `(void)`. QTest command-line flags such as `-v2`, `-o result.xml`, or `-testcase` cannot be passed to the binary even though the signature suggests they should work. This follows the same pattern as `test_xvue_qt_mail_menu.cpp` (Phase 6.1) and is an accepted constraint because `XvueApp::ensure()` already constructed `QApplication` with a fixed fake argv that must outlive the process. The issue is that there is no comment explaining why real argv is discarded, which will confuse the next developer who tries to pass `-v2`.

**Fix:** Add a brief comment:

```cpp
int main(int argc, char* argv[]) {
    // Real argc/argv cannot be forwarded to QTest::qExec because
    // XvueApp::ensure() (called below) constructs QApplication with a
    // fixed fake_argv that must have static lifetime. Forwarding real
    // argv here would leave a dangling pointer after main() returns.
    (void)argc; (void)argv;
```
