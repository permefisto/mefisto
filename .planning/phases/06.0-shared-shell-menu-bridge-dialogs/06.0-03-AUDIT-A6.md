# Audit A6 — MMB (middle-mouse-button) parity between Souris and Souris2

**Plan:** 06.0-03 Task 1
**Status:** RESOLVED — empirical reading of `xvue/xvuelc.c`
**Date:** 2026-04-19

## Question

Per Plan 06.0-RESEARCH.md §7 Pitfall 7.2, the [ASSUMED] state of A6 was: "MMB likely
aborts in BOTH Souris and Souris2 modes in the X11 reference; if true, Plan 05's pure
middle-drag pan must be revised to Ctrl+MMB to avoid colliding with the abort path."

This audit reads the X11 reference body in `xvue/xvuelc.c` to confirm or refute that
assumption empirically.

## Souris MMB behavior — `xvsouris_` body

**Reference:** `xvue/xvuelc.c:2183-2316` (`void proc(xvsouris)( int *notypeevent, int *nbc, int *x1, int *y1 )`)

The `xvsouris_` body branches on `event.type` inside its `XNextEvent` loop:

- `MotionNotify` (xvuelc.c:2248-2264): sets `*notypeevent = -2`, `*nbc = 1/2/3` per
  button. **Button2 sets `*nbc = 2` and nothing else** — `*notypeevent` stays at -2.
- `ButtonPress` (xvuelc.c:2266-2282): same pattern. **Button2 sets `*nbc = 2`,
  `*notypeevent = -1`** (press code, not abort).
- `ButtonRelease` (xvuelc.c:2284-2295): **Critical line — xvuelc.c:2290:**
  ```c
  else if (event.xbutton.button == Button2) {*nbc = 2;} /* 27/10/2010 *notypeevent=0;} */
  ```
  The trailing comment `/* 27/10/2010 *notypeevent=0;} */` documents that MMB used
  to abort here (set `*notypeevent = 0`) but the abort behavior was **explicitly
  removed on 2010-10-27**. Today MMB on release sets `*nbc = 2` and `*notypeevent = 1`
  (full click), exactly like LMB and RMB.
- `KeyPress` (xvuelc.c:2297-2312): unrelated to MMB.

**Verdict for Souris:** **MMB does NOT abort.** It is a normal mouse button with
`*nbc = 2`. The abort-on-MMB behavior was removed in 2010 (the comment is preserved
as historical evidence).

## Souris2 MMB behavior — `xvsouris2_` body

**Reference:** `xvue/xvuelc.c:2317-2480` (`void proc(xvsouris2)( int *items, int *pmin0, int *notypeevent, int *ibutton, int *x1, int *y1 )`)

The `xvsouris2_` body branches on `event.type`:

- `MotionNotify || ButtonPress` (xvuelc.c:2383-2440): single combined branch. Sets
  `*notypeevent = 5` (accrochage active) and:
  ```c
  if (event.xbutton.button == Button1)      *ibutton = 1;
  else if (event.xbutton.button == Button2) *ibutton = 2;
  else                                       *ibutton = 3;
  ```
  No abort on MMB. The accrochage nearest-item search runs identically for all three
  buttons; the nearest sprite is drawn and the call returns with `*notypeevent = 5`.
- `ButtonRelease` (xvuelc.c:2442-2463): erases the previously-drawn accrochage
  sprite and returns `*notypeevent = 1` (full click). MMB handling:
  ```c
  else if (event.xbutton.button == Button2) *ibutton=2 ;
  ```
  No abort.
- `KeyPress` (xvuelc.c:2465-2478): D-06 path; Esc/@ handled at the saclav.f layer
  per Phase 5 D-06. No MMB involvement.

**Verdict for Souris2:** **MMB does NOT abort.** Same as Souris — normal mouse button
with `*ibutton = 2`.

## Comparison with current Phase 5 Qt bridge

The current Qt-side `XvueEventBridge::eventFilter` (xvue_qt_event.cpp) DOES treat MMB
as abort in BOTH modes:

- **Souris**, xvue_qt_event.cpp:329-332:
  ```cpp
  if (me->button() == Qt::MiddleButton) {
      pending_.notypeevent = 0;
      pending_.nbc         = 2;
  }
  ```
  Comment: "X11 parity: middle-button historically aborts (see xvuelc.c:2272)" — this
  comment is **incorrect**. xvuelc.c:2272 sets `*notypeevent = -1` (press), not 0
  (abort). The historical abort was REMOVED in 2010 per the xvuelc.c:2290 comment.
- **Souris2**, xvue_qt_event.cpp:275-283: also returns `notypeevent = 0, nbc = 2`
  on MMB press.

The Qt bridge is therefore stricter than the X11 reference: it aborts on MMB while
xvuelc.c does not. This is a **Phase 5 deviation from the X11 reference**, not a
Plan 03 finding — it pre-dates Plan 03 and was committed in the Phase 5 plans.

**This audit does NOT change Phase 5 behavior.** Modifying the Phase 5 bridge MMB
branches is out of scope for Plan 03 (the plan explicitly limits source changes to
`xvue_qt_event.cpp::waitForEvent` pre-drain + MouseMove emit). The MMB-abort
divergence is logged here as a follow-up item for a future phase or hotfix. It does
not block Plan 05's pan path because:

1. Plan 05's pan handler only runs when `loop_ == nullptr` (idle mode); the bridge
   filter eats MMB only when `loop_ != nullptr` (during Souris/Souris2 reads).
2. The Phase 5 abort-on-MMB inside `loop_ != nullptr` matches the bridge's existing
   shipped behavior — no Plan 05 user can pan during a blocking read because the
   bridge intercepts MMB first. Plan 05's pan only fires between blocking reads.

## Verdict for Plan 05 pan

**Plan 05 pan impl: OK as pure MMB.**

Reasoning:
- The X11 reference (`xvuelc.c`) does NOT abort on MMB in EITHER Souris or Souris2.
- The Phase 5 Qt bridge DOES abort on MMB during blocking reads (a deviation from
  X11) — but Plan 05's pan only runs OUTSIDE blocking reads (when `loop_ == nullptr`).
- The two paths (bridge MMB-abort during blocking; canvas MMB-pan when idle) co-exist
  cleanly because Qt event order is `eventFilter -> widget handler` and the bridge
  short-circuits when active.

Plan 05 does **NOT** need revision to Ctrl+MMB. The current pure MMB pan binding
is safe to ship.

## Follow-up flag for a future phase

The Phase 5 Qt bridge's MMB-abort inside `loop_ != nullptr` is a deviation from the
2010-revised X11 reference behavior (xvuelc.c never aborts on MMB anymore). If a
user during a blocking read in Souris mode (e.g., a single-click selection prompt)
clicks the middle button, the X11 backend treats it as a normal MMB press while
the Qt backend silently aborts the read. This is an **A/B mismatch**, not a Plan 03
or Plan 05 deviation — both plans inherit Phase 5's existing bridge MMB handling.

A future plan (Phase 7 cleanup or a Phase 6.x hotfix) should consider:
- Either align the Qt bridge with xvuelc.c (drop the abort, treat MMB as a normal
  button with `notypeevent = -1, nbc = 2`).
- Or document the divergence as a deliberate Qt-side improvement (MMB = abort is
  arguably more useful UX than treating MMB as a click that goes nowhere) and
  update xvue/qt/README.md accordingly.

This audit recommends documenting and deferring; no immediate action is required
for Plan 03, Plan 05, or the rest of Phase 6.0.
