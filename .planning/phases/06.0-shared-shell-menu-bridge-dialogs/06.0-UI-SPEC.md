# Phase 6 — UI Design Contract

> Visual and interaction contract for the Qt 6 `QMainWindow` shell + per-module
> menu surface. This is a scientific-computing desktop app (MEFISTO), **not**
> a web SPA — the template's 6-dimension structure is preserved, but the
> content is adapted to Qt conventions (QPalette / QStyle / QFontMetrics)
> instead of CSS tokens. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope:** Phase 6 is split into **6.0** (shared shell this document fully specifies)
and **6.1..6.5** (per-module menu wiring that *extends* 6.0). This UI-SPEC
defines the *contract* both layers conform to so the planner can write
module-specific plans that all conform to one visual and interaction contract.

## Design System

| Property | Value |
|----------|-------|
| Tool | Qt 6 (no shadcn — Qt 6.10 from Debian apt owns design-system state) |
| Preset | not applicable (Qt `QStyle` + system palette is the preset) |
| Component library | Qt Widgets (`QMenuBar`, `QToolBar`, `QStatusBar`, `QDockWidget`, `QDialog`, `QMessageBox`, `QFileDialog`, `QSettings`) |
| Icon library | Qt built-in `QStyle::StandardPixmap` primary + custom SVG under `xvue/qt/resources/icons/` for mesh-specific actions (D-10) |
| Font (chrome) | Qt system default font via `QApplication::font()` — follows platform/user preference; HiDPI/dark-mode aware |
| Font (canvas) | Bundled `DejaVuSansMono.ttf` from `xvue/qt/resources/xvue_fonts.qrc` loaded by `XvueApp::load_bundled_font_()` — **unchanged** by Phase 6, frozen by TEXT-06 |
| Style | System-follow (`QApplication::setStyle` never called) — `QApplication::palette()` tracks system dark/light (D-05) |
| Translation | **File-flag lookup table** (not `QTranslator`) — `$MEFISTO/td/m/anglais` existence selects EN; absent → FR (D-02 inherited, UX-08). See `.planning/phases/06-.../.../i18n-strategy.md` note below. |

**Font rationale:** The canvas (backing pixmap) has its own bundled font
frozen against the system look. Only the *chrome* (menus, toolbars, dialogs,
dock widgets, status bar) uses Qt's system font so dark-mode and HiDPI work
for free. This mirrors D-05: chrome follows system; canvas pixels do not.

**i18n strategy (decided here, ratified from UX-08 + D-06 of Phase 5):**
A simple compile-time bilingual lookup table (`std::array<std::pair<const char*, const char*>, N>` or equivalent, indexed by an enum) is used in preference to Qt's `QTranslator` / `.ts` files. Rationale:
1. All user-visible strings in v1 are a fixed, finite set (~120–180 strings total — menus + tooltips + status messages + About + dialog buttons).
2. MEFISTO's existing bilingual mechanism (`$MEFISTO/td/m/anglais` file-existence check) is load-bearing for the non-Qt side (launcher scripts `bin/INITIER`, `bin/MAILLER`, etc. detect it via `test -f`). Using the same mechanism inside Qt keeps one source of truth.
3. `QTranslator` live-switching is explicitly out of scope per PROJECT.md "Out of Scope" table. Process-restart-to-change-language is sufficient and is what users already expect.
4. No toolchain dependency on `lrelease` / `lupdate` / `.qm` compilation — matches the no-CI / single-developer posture.

Implementation sketch (planner will refine):
```cpp
// xvue/qt/src/xvue_qt_i18n.h
enum class MsgId : int { FileMenuTitle, FileOpen, FileSave, FileQuit, ... };
bool xvueIsEnglish();          // reads $MEFISTO/td/m/anglais once, caches
const char* tr(MsgId id);      // returns FR or EN pointer
// Convenience: QString xvueT(MsgId id) -> QString::fromUtf8(tr(id))
```

The strings table is authoritative — all menu / tooltip / status / dialog
copy in this UI-SPEC Copywriting Contract section must have an entry in the
table with both a FR and an EN form.

## Spacing Scale

Qt 6 does not use a design-token spacing scale the way CSS does — layouts
come from `QHBoxLayout` / `QVBoxLayout` / `QGridLayout` + the platform
`QStyle` pixel metrics (`PM_DefaultFrameWidth`, `PM_ToolBarItemSpacing`, etc.).
To keep this contract conformable with the checker's dimension model, we
declare the **explicit spacing values** Phase 6 code is allowed to hand-set
(everything else must defer to `QStyle`).

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4 px | `QLayout::setSpacing(4)` inside dock-widget inner panels; icon-to-label gap inside custom toolbar widgets |
| sm | 8 px | `QLayout::setContentsMargins(8, 8, 8, 8)` for dialog inner panels (Preferences, About) |
| md | 16 px | `QLayout::setContentsMargins(16, 16, 16, 16)` for the About dialog outer frame; status-bar mouse-coord readout left-padding |
| lg | 24 px | Not used in 6.0 — reserved for 6.1..6.5 module dialogs |
| xl | 32 px | Not used in 6.0 |

**Exceptions (Qt-governed, NOT hand-set by Phase 6 code):**

- **Menu-bar height**: `QStyle::pixelMetric(PM_MenuBarFrameWidth)` + font metrics — NOT hand-set.
- **Toolbar icon size**: see Iconography section (declared 22 px logical, scales on HiDPI via `devicePixelRatio`).
- **Status-bar height**: `QStyle` default (~20–24 px depending on platform) — NOT hand-set.
- **Dock-widget title-bar height**: Qt default — NOT hand-set.
- **Toolbar separator gap, menu-item padding**: `QStyle` governed — NOT hand-set.
- **HiDPI scaling**: all declared values above are **logical pixels**. Qt multiplies by `devicePixelRatio` automatically per SHELL-06.

**Rule:** If Phase 6 code contains a `setContentsMargins` or `setSpacing` call
with a value NOT in the {4, 8, 16, 24, 32} set, that is a violation requiring
justification. All other pixel values must come from `QStyle::pixelMetric`
or `QFontMetrics`.

## Typography

Qt widgets inherit fonts from `QApplication::font()` (the system font) by
default. Phase 6 code **must not** call `setFont()` on chrome widgets
(menu bar, toolbar, status bar, dock widget, dialogs). The canvas keeps its
own bundled monospace font per TEXT-06 (frozen, separate concern).

Declared type roles and their sources:

| Role | Source | Typical size* | Weight | Usage |
|------|--------|---------------|--------|-------|
| Body | `QApplication::font()` | ~10–11 pt | Normal (400) | Menu labels, toolbar tooltips, dialog body text, dock widget content |
| Label | `QApplication::font()` | ~10–11 pt | Normal (400) | Status-bar coord readout, form field labels |
| Heading | `QApplication::font()` (boldened) | ~10–11 pt | Bold (700) | Dialog section headings (e.g. Preferences tab labels), `QGroupBox::title` |
| Display | `QApplication::font()` (size +4) | ~14–15 pt | Bold (700) | About dialog product name "MEFISTO" |
| Canvas mono | `DejaVuSansMono` (bundled, Phase 3) | 12 px | Normal | Node-number labels, scientific text — **Phase 6 does not touch this** |

*Typical sizes are platform-dependent; the exact pt size comes from the
user's desktop environment. Phase 6 code reads them via `QApplication::font().pointSize()`
and derives display/heading by `QFont::setBold(true)` and/or
`f.setPointSize(f.pointSize() + 4)` — **never by hard-coded point values**.

**Line height:** Qt `QFontMetrics::height()` governs line height in text
widgets. Not configurable by Phase 6 code.

**Rationale for "only 2 weights":** Qt's system font delivers Normal and Bold
in every Linux desktop. Italic/Light/etc. are avoided — they depend on the
installed font, and MEFISTO's bilingual labels in bold italic look
inconsistent across French/English font coverage.

## Color

Phase 6 delegates chrome coloring **entirely to `QPalette`** (system dark/light
follow per D-05). The canvas region is carved out of the palette system —
scientific colormaps loaded via `PALCDE` / `XvCouleursImposees` render into
`XvueState::backing_pixmap_` and are composited onto the widget
ignoring `QPalette` (TEXT-06).

| Role | Value | Source | Usage |
|------|-------|--------|-------|
| Dominant (60%) | `QPalette::Window` | System | `QMainWindow` background, dock widget background, dialog background |
| Secondary (30%) | `QPalette::Base` | System | Dock widget content area (e.g. console log text area), dialog input fields, file-dialog list |
| Accent (10%) | `QPalette::Highlight` | System | Selected menu item, selected toolbar action, hover on dock title, text selection inside console log |
| Destructive | `QPalette::BrightText` on red background (`QMessageBox::Critical` default) | System + Qt default | **Only** in `QMessageBox::critical()` for `*** ERREUR` alerts (UX-11) and destructive confirmations |
| Informational | `QMessageBox::Information` default colors | Qt default | Non-error status-bar 3s messages surfaced as fall-back when status bar is hidden |
| **Canvas region** | **Not governed by QPalette** | `XvueState` | Backing pixmap pixels controlled by `XvCouleursImposees` — frozen per TEXT-06 |

**Accent reserved for (exhaustive list):**
1. Currently-selected menu item (Qt standard, not overridden).
2. Currently-hovered toolbar QAction (Qt standard, not overridden).
3. Selected text inside console dock widget.
4. Keyboard focus ring on dialog buttons (Qt standard).
5. "Recent Projects" submenu most-recent entry bold indicator (if planner keeps the bold; may be dropped).

**NOT accented (explicit):** toolbar separator lines, dock-widget title bars
(they use `QPalette::Window`), status-bar text (uses `QPalette::WindowText`),
menu-bar background (uses `QPalette::Window`). This preserves visual quiet
on a scientific-computing tool where attention must stay on the canvas data.

**Dark-mode test:** Toggling the desktop environment's dark-mode theme and
restarting `pp/ppmail_qt` must produce a window where:
- All chrome re-colors (menu bar, toolbar, status bar, dock, dialogs).
- The canvas backing pixmap is **visually identical** to light-mode (pixel-level, by design).
- Scientific colormaps (stress / temperature / velocity) render unchanged.
This is Phase 6's dark-mode acceptance test, to be validated manually
during 6.0 sign-off (VALID-01 extension).

**Status-bar message color convention:**
- Informational (3s auto-clear): default `QStatusBar::showMessage` styling.
- Error (*** ERREUR line): `QMessageBox::warning` modal (not in-status-bar), per UX-11.
- Refuse-modal-reentry (D-08): default `QStatusBar` styling — message body carries the meaning: `"Finish current operation first (type 99;)"` / `"Terminez l'opération en cours (tapez 99;)"`.

### Toolbar (6.0 shared)

A single horizontal toolbar, `QToolBar::setIconSize(QSize(22, 22))`,
positioned under the menu bar. Actions share `QAction` instances with the
menu bar (Qt's built-in aliasing — set the same QAction on both).

Default toolbar contents (6.0): `[Open] [Save] | [ZoomIn] [ZoomOut] [Fit] | [Console-toggle]`
(pipe = `QToolBar::addSeparator()`).

Modules extend via their own `addAction` calls after the shared contents.

### Status bar (6.0 contract)

Two zones:
1. **Permanent (right-aligned)** — mouse coord readout `addPermanentWidget(QLabel)` updated on canvas `mouseMoveEvent` (UX-12). Format: `X: %4d  Y: %4d` (logical canvas pixels). Cleared on `leaveEvent`.
2. **Transient (left-aligned)** — `showMessage(text, 3000)` 3-second auto-clear used for: modal-refuse message (D-08), menu hover tooltips (Qt default), QAction status tips (set via `QAction::setStatusTip`).

### Console dock (UX-10, UX-11, D-07)

Widget: `QDockWidget` titled `Console` (EN) / `Console` (FR — same string),
containing a `QPlainTextEdit` in read-only mode, monospace font
(`QFontDatabase::systemFont(QFontDatabase::FixedFont)` — NOT the bundled
canvas font; follows system mono).

- **Input source:** `freopen`-based stdout redirection into a `QSocketNotifier`-watched pipe (per CONTEXT `code_context` — same-process pipe-reader, NOT `QProcess`).
- **Behavior:** Auto-scroll to bottom on new lines. Copy-to-clipboard action in context menu. No clear-log action in v1 (session-local, resets on process start per D-07).
- **Error parsing:** Any line matching regex `^\*\*\* ERREUR` (or `^\*\*\* ERROR`) triggers `QMessageBox::warning(nullptr, "MEFISTO Error" / "Erreur MEFISTO", line_body)`. Subsequent matching lines within 500 ms are batched into one message box to avoid cascade (planner decides exact batching; this is the policy).
- **Max log size:** 10 000 lines cap via `QPlainTextEdit::setMaximumBlockCount(10000)` — prevents unbounded growth during long meshing sessions.

## Interaction Contracts

This section is the **interaction contract** — the rules of engagement
between user input, QAction routing, the canvas, and the Fortran lexicon.
This is the most load-bearing part of the UI-SPEC because it encodes the
"Fortran must not notice" invariant for the UX layer.

### Modifier rule (D-04 — LOCKED)

| Input | Routing |
|-------|---------|
| `Ctrl+X`, `Alt+X`, `Ctrl+Shift+X`, `Ctrl+Alt+X` (any modifier + letter/digit) | `QShortcut` on `QMainWindow` → `QAction::triggered` → `XvueMenuBridge::pendingCommands_.push(...)` → next `xvsouris_` drains and returns synthetic `notypeevent=2` keyboard event (UX-02, UX-03) |
| `F1..F12` | `QShortcut` on `QMainWindow` → same QAction path |
| Plain alphanumeric (`a`..`z`, `0`..`9`) | Routed to focused widget (canvas has `StrongFocus` — Phase 5 D-02) → `XvueEventBridge` filter → Fortran via `xvsouris_` `nbc` return (typed lexicon UNCHANGED) |
| `;` (lexicon delimiter) | Same path as plain alphanumeric — MUST reach Fortran verbatim |
| `@` (AZERTY Esc alias, Phase 5 D-06) | Same path as plain alphanumeric — mapped to `nbc=64` by bridge |
| `Esc` | Same path — mapped to `nbc=27` by bridge (Phase 5 D-06) |
| `Return` | Same path — mapped to `nbc=13` by bridge |
| `Tab` | Qt focus-rotation INTERCEPTED when modifier+something maps to a shortcut; otherwise canvas consumes it → `nbc=9` |

**Critical implementation rule (6.0 shell):** All `QShortcut` objects in 6.0
and 6.1..6.5 MUST be constructed with `Qt::WindowShortcut` context (Qt default)
**never** `Qt::ApplicationShortcut` (would steal focus from the canvas) and
**never** `Qt::WidgetShortcut` installed on the canvas (would break modifier
combos). Planner enforces via grep check.

**The menu-queue dispatch pattern (UX-02, UX-03 — LOCKED):**
```
QAction::triggered (user clicks menu item "Add Vertex")
    -> XvueMenuBridge::queueCommand(lexicon_string)        // non-blocking, no Fortran call
    -> XvueMenuBridge::pendingCommands_.push_back(...)
    -> (control returns to Qt event loop immediately — CRITICAL)

(later, when Fortran executes CALL XVSOURIS)
xvsouris_ -> XvueEventBridge::waitForEvent()
          -> before entering QEventLoop::exec(): check pendingCommands_
          -> if non-empty: pop head, format as synthetic notypeevent=2 key event, RETURN immediately without blocking
          -> else: enter event loop as per Phase 5
```

The bridge therefore has TWO queues visible at `waitForEvent` entry:
1. Menu-bridge `pendingCommands_` (Phase 6) — polled FIRST.
2. Real Qt events (Phase 5 bridge).

Order is menu-queue-first so a rapid user workflow ("click menu, then move mouse") still executes the menu command before the next motion arrives.

### Canvas interaction (UX-12)

The canvas is `XvueCanvas` (Phase 1, `StrongFocus` + `setMouseTracking(true)` from Phase 5). Phase 6 adds:

| Gesture | Behavior | Where implemented |
|---------|----------|-------------------|
| Left-click | Dispatched to `XvueEventBridge::eventFilter` → `xvsouris_` returns `ncb=1`. **Phase 6 does not change this** — Phase 5 semantic preserved. | (Phase 5 existing) |
| Middle-click drag | Pan canvas viewport. Implementation: on mouse-press record anchor, on move `XvueState::pan_offset_ += delta` + request `update()`. Middle-release commits. **Does NOT dispatch to Fortran** — pure Qt-side transform on the backing pixmap display. | `XvueCanvas::mousePressEvent/mouseMoveEvent/mouseReleaseEvent` extended in 6.0 |
| Right-click | Opens **context menu** (`QMenu`) populated with the top ~6 most-frequent module-specific QActions (per the LEXICON-AUDIT frequency data). Suppressed if `blockingDepth() > 0` (see Modal guard). | `XvueCanvas::contextMenuEvent` override added in 6.0 (populated by module in 6.1..6.5) |
| Wheel | Zoom canvas viewport. Direction: wheel-up = zoom-in. Factor: 1.15× per notch (`event->angleDelta().y() / 120`). **Does NOT dispatch to Fortran**. | `XvueCanvas::wheelEvent` override added in 6.0 |
| Mouse move (no button) | Update status-bar coord readout (X/Y in canvas logical px). Also feeds `XvueEventBridge` for Phase 5 compat. | `XvueCanvas::mouseMoveEvent` extended in 6.0 |

**Zoom/pan invariants (critical):**
- Middle-drag pan and wheel zoom manipulate a Qt-side view transform applied at `drawPixmap` time in `paintEvent`. They DO NOT modify `XvueState::backing_pixmap_`. This is the "Fortran must not notice" invariant at the UX layer — Fortran draw commands always paint in canonical pixel coordinates; the view transform is purely cosmetic.
- Resetting the view is `View → Fit to Window` (`Ctrl+0`) — QAction that does `XvueCanvas::resetView()` (no Fortran dispatch).
- Future (Phase 7+): export operations must capture the *current view transform* (zoomed/panned), not the raw backing pixmap. Documented as a Phase 7 concern here.

### Modal dialog re-entrancy guard (D-08, UX-04 — LOCKED)

Every `QDialog::exec()`-invoking QAction handler MUST wrap the call in the
guard helper:

```cpp
void XvueWindow::openFileDialog() {
    if (XvueApp::blockingDepth() > 0) {
        statusBar()->showMessage(
            xvueT(MsgId::ModalRefuse),   // "Finish current operation first (type 99;)" / "Terminez l'opération en cours (tapez 99;)"
            3000);                       // 3-second auto-clear
        return;
    }
    QFileDialog dlg(...);
    dlg.exec();
}
```

- Status-bar message duration: **3000 ms** (locked).
- QAction remains **clickable** (not `setEnabled(false)`). Rationale: disabled items are mute — they don't explain themselves. The message body is the explanation.
- Applies to: `QFileDialog::exec`, `QDialog::exec` in Preferences, About, and all module-specific dialogs.
- Does NOT apply to `QMessageBox::warning` from `*** ERREUR` (these are passive — the solver is already blocked-on-event from Fortran; the message box is informational and the user dismisses it).

### Keyboard focus policy (contract)

- `XvueCanvas::focusPolicy()` is `Qt::StrongFocus` (set in Phase 5 — LOCKED, must not change).
- `QMainWindow::focusPolicy()` default (`Qt::NoFocus`) — unchanged.
- Menu bar and toolbar naturally handle their own focus via Qt's keyboard-nav path (Alt opens the menu bar; arrow keys traverse items).
- On window raise / first show, `XvueCanvas::setFocus()` is called so `99;`-style input works immediately without a click.
- Clicking a menu item returns focus to the canvas after dispatch (`QMenu::aboutToHide` → `canvas->setFocus()`). This preserves the "type 99;" muscle memory without requiring the user to re-click the canvas.

### Accessibility

Qt widgets are accessible by default; Phase 6 must not regress this.

- Every `QAction` sets `setToolTip(localized_label_with_shortcut)` and `setStatusTip(one_line_description)`.
- `QAction::setShortcut` text automatically appears in menu items (Qt default) and in tooltips (via the `setToolTip` string we compose).
- Screen readers (Orca on Debian) read QActions by their text; bilingual EN/FR is preserved per `xvueT()` strings.
- Keyboard-only navigation: Tab order through dialogs uses Qt default; no custom `setTabOrder`. Menu bar is reachable via Alt; canvas is reachable via Shift+Tab from the menu bar (Qt default).
- High-contrast: system-follow `QPalette` already handles high-contrast themes on KDE/GNOME. No special code path.

## Per-Module Conformance Contract (6.1..6.5)

This section is the **contract each of 6.1..6.5 extends**, NOT the full
content (which is audited per-module). It defines the *shape* module plans
must produce.

### Each module must produce

1. **`LEXICON-AUDIT.md`** — complete enumeration of every typed-lexicon
   command in that module's `.f` drivers (exhaustive, D-03). Schema:

   ```markdown
   # <Module> Lexicon Audit

   ## Menu: <mesh / solve>
   ### <Group> (e.g. "Generate", "Refine", "Geometry")

   | Lexicon input | FR label | EN label | Shortcut | Toolbar? | Icon | Frequency (H/M/L) | Fortran dispatch | Surfaced as QAction? |
   |---------------|----------|----------|----------|----------|------|-------------------|------------------|----------------------|
   | `5;90;` | Ajouter sommet | Add vertex | `Ctrl+V` | yes | `add-vertex.svg` | H | `mail/aisommet.f::A1LGSOM` | yes |
   | `7;12;` | Joindre arête | Join edge | — | no | — | L | `mail/aijoin.f::AIJOIN` | no (long-tail) |
   | ... | ... | ... | ... | ... | ... | ... | ... | ... |
   ```

2. **QAction registration code** in `prpr/pp*_qt.f` (or a thin C++ wrapper
   invoked from it). Module-specific menus are added AFTER `XvueApp::ensure()`
   and BEFORE the event loop is entered.

3. **Frequency cutoff decision** recorded in the module's plan: which
   entries earn a QAction (High + Medium frequency) vs stay typed-only (Low).
   Target: 20–40 QActions per module (CONTEXT D-03).

4. **Bilingual strings** for every new label / tooltip / status tip, added
   to the `xvue_qt_i18n.cpp` string table.

### Each module MUST NOT

- Change `XvueCanvas`, `XvueWindow`, `XvueApp`, `XvueEventBridge`, or
  `XvueState` structural shape (touching file owners is 6.0 territory).
- Define its own color / font / spacing / icon-size values. Reuse 6.0
  tokens or justify exception in the plan.
- Introduce a shortcut that collides with a 6.0-reserved combo
  (`Ctrl+{O,S,E,Q,+,-,0,,}`, `F1`, `F9`).
- Bypass the `XvueMenuBridge::pendingCommands_` queue — every menu action
  MUST dispatch via the queue, never directly into Fortran.
- Introduce plain-char (no-modifier) shortcuts — violates D-04.

### Module menu ordering template

```
{File (shared)}  {Edit (module-optional)}  {<Module-main>}  {View (shared)}  {Help (shared)}
```

Each module's `<Module-main>` menu may have sub-menus (e.g. Mesh →
Generate ▶, Refine ▶, Edit Geometry ▶). Sub-menus are grouped by the
module's semantic clustering, not alphabetically.
