## Decisions Made

- **Stack-allocated widgets in tests** — Heap-allocated QDockWidget/QDialog with parent=nullptr survived past `delete` due to D-08's leaked QApplication holding references via topLevelWidgets list. Stack-allocated test fixtures destruct in deterministic LIFO order before QApplication's atexit runs. Mirrors the legacy event-loop teardown sequence.
- **AUTORCC + .qrc target_source instead of qt_add_resources(FILES "")** — `qt_add_resources` with empty FILES list is fragile across Qt 6.x versions; some emit a CMake error, some emit empty .cpp objects that fail to link. Plans 6.1..6.5 will append `<file>icons/foo.svg</file>` lines to xvue_icons.qrc directly — AUTORCC picks them up automatically with no further CMake edits.
- **MsgId enum locked at 47 entries** — UI-SPEC §Copywriting Contract enumerates the exact set; locking the enum width here means Plan 02's lookup table can ship a `static_assert(static_cast<int>(_Count_) == 47)` exact-size check without re-syncing with the spec.
- **xvue_module_init_ stub printed-name length clamp at 32 chars** — T-06.0-01-01 mitigation. Module names ('mail', 'elas', 'flui', 'ther', 'nlse') are all ≤4 chars, so 32 is generously above the maximum and well below any reasonable buffer-overflow surface.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Stack-allocated widgets in testScaffoldIsLinkable to avoid exit-time segfault**
- **Found during:** Task 1 verification (test execution after first build)
- **Issue:** Initial test body heap-allocated XvueConsoleDock/XvuePreferencesDialog/XvueRecentProjectsMenu with `new`, then `delete` at end of test. Tests passed (5/5) but the binary segfaulted (exit 139) at process exit during QApplication-shutdown atexit handler. Root cause: D-08 leaked QApplication holds references to top-level QWidgets via `qApp->topLevelWidgets()`; once `XvueApp::ensure()` ran (inside main() to set AA_CompressHighFrequencyEvents), the heap-allocated test widgets were tracked even after `delete`. Existing xvue_qt_event_tests doesn't hit this because it opens/closes a real window via `xvfermer_()` which drains the deleteLater queue with `processEvents(ExcludeUserInputEvents)`.
- **Fix:** Switched to stack allocation for all 5 fixtures (XvueMenuBridge, XvueConsoleDock, XvueErrorBatcher, XvuePreferencesDialog, XvueRecentProjectsMenu). Added `cleanup()` and `cleanupTestCase()` slots that call `processEvents(ExcludeUserInputEvents)` to drain Qt's deleteLater queue between tests + at teardown. Mirrors xvfermer_'s pattern for the same root cause.
- **Files modified:** xvue/qt/tests/test_xvue_qt_menu_scaffold.cpp
- **Verification:** 5 consecutive runs of `xvfb-run xvue_qt_menu_tests` exit 0, all 3 tests + initTestCase + cleanupTestCase PASS.
- **Committed in:** bfb165a (Task commit 4 — same logical wiring step that introduced the test file)

**Total deviations:** 1 auto-fixed (Rule 1 — bug surfaced by verification, not present in plan's `<action>` spec which assumed `new`+`delete` was sufficient)
**Impact on plan:** Stack-allocation pattern is strictly safer and should be the default for all future scaffold tests in Phase 6.0. No scope creep — the test still asserts exactly what the plan specified (each class is linkable + constructs without crash).

## Issues Encountered

- **Compiler PATH mismatch at first cmake configure** — `gcc`/`g++` are not on the default PATH; only versioned `gcc-14`/`g++-14` exist. STATE.md noted the workaround: prepend `/tmp/gfortran-14-shim` to PATH (symlinks gcc→gcc-14, g++→g++-14, gfortran→gfortran-14) and export `CC=/tmp/gfortran-14-shim/gcc CXX=/tmp/gfortran-14-shim/g++`. Once that env was in place, cmake configure + build succeeded immediately. This is a project-environment recipe, not a Plan 01 deviation.
- **MEFISTO env var unset in fresh shell** — Build scripts (`bin/cbl_tout_qt`, etc.) require `$MEFISTO` to point at the worktree root. Set explicitly per build invocation (`export MEFISTO=/home/drico/git/mefisto/.claude/worktrees/agent-a89f4b3e`).
