## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] XvueConsoleDock::installStdoutRedirect hijacks QtTest reporter output**
- **Found during:** Task 3 verification (first run of `xvue_qt_window_chrome_tests` after wiring).
- **Issue:** Once `xvue_module_init_("mail", &len)` was called inside `testModuleInitMarksBridgeRegistered`, the dispatch body's step 3 (`win->consoleDock()->installStdoutRedirect()`) ran `dup2(fd[1], STDOUT_FILENO)` over QtTest's stdout. All subsequent QtTest output (PASS/FAIL/Totals lines for the remaining 2 tests) was silently consumed by the dock's QSocketNotifier. The tests themselves PASSED (binary exited 0), but the suite report appeared truncated at `testFitToWindowResetsCanvas` — testModuleInitMarksBridgeRegistered + testModuleInitFlipsHasUserContent + cleanupTestCase + Totals were all swallowed.
- **Fix:** Added `XVUE_QT_DISABLE_STDOUT_REDIRECT` env-var early-return guard at the top of `XvueConsoleDock::installStdoutRedirect()`. When the var is set to a non-empty non-"0" value, the function returns before the pipe()/dup2() sequence. The test main sets `qputenv("XVUE_QT_DISABLE_STDOUT_REDIRECT", "1")` before XvueApp::ensure() so production code path is unchanged but the QtTest binary keeps its stdout intact. Production pp*_qt invocations never set the var.
- **Files modified:** xvue/qt/src/xvue_qt_console_dock.cpp (env var guard + `<cstdlib>` include), xvue/qt/tests/test_xvue_qt_window_chrome.cpp (qputenv in main).
- **Verification:** Re-run of xvfb-run xvue_qt_window_chrome_tests showed all 16 PASS lines including testModuleInit* and Totals (16 passed, 0 failed, 0 skipped, 0 blacklisted, 70ms).
- **Committed in:** `66a6805` (Task 3 commit — same logical scope as the test file landing).
- **Documented in:** xvue_qt_console_dock.cpp inline comment + commit message body.

---

**Total deviations:** 1 auto-fixed (Rule 1 — bug surfaced by verification).
**Impact on plan:** The fix preserves production behavior (default = redirect). The test-isolation knob is well-defined contract. Without the fix, the 14-case QTest suite would appear to pass-but-truncate, which would falsely satisfy acceptance criterion 3 ("10 tests pass") only because the binary returns exit 0. The fix makes the suite output trustworthy.

## 6.1..6.5 Integration Contract

Each per-module phase (6.1=mail, 6.2=elas, 6.3=flui, 6.4=ther, 6.5=nlse) must:

1. **Add `void registerXxxActions(XvueWindow*, XvueMenuBridge*)` as a stronger symbol** (without the `_stub_` suffix) in a new file `xvue/qt/src/xvue_qt_<module>_actions.cpp`. The function should populate the module-specific menus/toolbar items and connect QAction::triggered handlers to either:
   - `bridge->queueLexicon("...")` to drive the typed-lexicon dispatch via Plan 03's pre-drain, OR
   - direct C++ work that sidesteps the lexicon (e.g., a Qt-native dialog).
2. **Add `CALL XVUE_MODULE_INIT('<name>')` in `prpr/pp<module>.f`** BEFORE the existing `CALL XVINITGRAPHIQUE()` line. The `<name>` must be one of {mail, elas, flui, ther, nlse}.
3. **Add the new .cpp to `xvue/qt/CMakeLists.txt`** so libxvueqt.a links the stronger symbol. The link order ensures the new symbol displaces the anonymous-namespace `_stub_` in xvue_qt_api.cpp.
4. **Update `xvue/qt/cmake/verify_abi.sh`** if the module adds any new extern "C" entries (none expected for 6.1..6.5 — module dispatch is internal, not Fortran-facing).

After 6.1..6.5 land, `xvue_module_init_` calls will exercise the real per-module bodies; the stubs become dead code (the linker selects the stronger symbol). Both the stub and the real implementation share the same `(XvueWindow*, XvueMenuBridge*)` signature so the dispatch site needs no per-module change.
