## Decisions Made

- **Pre-drain at TWO sites (xvsouris_ wrapper + waitForEvent).** AUTOEXIT lives in xvue_qt_api.cpp::xvsouris_, NOT in waitForEvent. If pre-drain only existed in waitForEvent, the production xvsouris_ path would short-circuit on AUTOEXIT before reaching waitForEvent and the menu queue would lose. The xvsouris_ site is what beats AUTOEXIT. The waitForEvent site is defense-in-depth for direct waitForEvent callers (Phase 5 unit tests use `XvueEventBridge bridge(canvas); bridge.waitForEvent(...)` patterns that bypass the wrapper). `testPreDrainPreservesDepth` deliberately exercises the in-bridge path so the BlockingDepthGuard RAII assertion is meaningful.
- **WaitMode::Souris guard in the in-bridge pre-drain.** xvsouris2_ (accrochage) and xvpause_ (key-gate per Phase 5 D-06) MUST NOT consume queued menu chars — their state machines depend on real mouse/key events. Two test cases (testPreDrainIgnoredInSouris2Mode, testPreDrainIgnoredInPauseMode) verify the queue stays intact across xvsouris2_/xvpause_ AUTOEXIT short-circuits. Note: the xvsouris_ wrapper-site pre-drain is implicitly Souris-mode-only because it's in the xvsouris_ entry; xvsouris2_ and xvpause_ wrappers are SEPARATE functions with their own AUTOEXIT and never touch the menu queue.
- **A6 audit findings.** Empirical reading of xvuelc.c shows MMB does not abort in either Souris or Souris2. The Phase 5 Qt bridge's MMB-abort during blocking reads is a deviation from the X11 reference — flagged as follow-up but NOT fixed by Plan 03 (out of scope; Plan 03 limits source changes to waitForEvent's pre-drain + MouseMove emit). Plan 05's pure MMB pan binding remains correct because the bridge eats MMB only when blocking; pan only fires when idle.
- **Plan 03 owns the new tests/CMakeLists.txt addition.** Plan 02's single-writer contract was for parallel-Wave-2 plans (02, 04, 05) on a shared file. Plan 03 is Wave 3 (runs after Wave 2 merges), so adding a fresh `add_executable` block in this worktree is conflict-free.

**1. [Rule 3 - Blocking] Pre-drain MUST exist in xvsouris_ wrapper too — AUTOEXIT lives there, not in waitForEvent**
- **Found during:** Task 2 design review (reading xvue_qt_api.cpp::proc(xvsouris) before writing the test file).
- **Issue:** Plan 03 spec says pre-drain block goes in `xvue_qt_event.cpp::waitForEvent` and lists ordering "BlockingDepthGuard ctor → menu-queue pre-drain → AUTOEXIT short-circuit → loop.exec()" as if AUTOEXIT lives inside waitForEvent. - **Fix:** Added the SAME pre-drain block to the top of `proc(xvsouris)` in xvue/qt/src/xvue_qt_api.cpp BEFORE the AUTOEXIT short-circuit. Defense-in-depth: the in-bridge pre-drain in waitForEvent stays as written (covers direct waitForEvent callers from Phase 5 tests).
- **Files modified:** `xvue/qt/src/xvue_qt_api.cpp` (also added include for xvue_qt_menu_bridge.h).
- **Verification:** `testPreDrainBeforeAutoexit` PASSES — first xvsouris_ returns 'x' (pre-drain wins), second returns CR=13 (queue's trailing CR), third returns SPACE=32 (AUTOEXIT path). Without the wrapper-site pre-drain this test would fail at the first assertion.
- **Committed in:** `a0c993a` (Task 2 source commit).
